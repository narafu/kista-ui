# KISTA UI/UX 단계별 개선 — 디자인 문서

- 작성일: 2026-07-12
- 상태: 사용자 승인 완료 (섹션 A·B·C)
- 다음 단계: writing-plans 스킬로 구현 플랜 작성

## 배경

kista-ui는 로즈골드 팔레트 + Pretendard/Cormorant Garamond 기반의 정교한 디자인 시스템(라이트·다크모드, 시맨틱 토큰, glass-card)을 이미 갖추고 있다. 이번 작업은 시스템 교체가 아니라 **일관성 정리 → UX 흐름 개선 → 비주얼 심화**의 단계별 전체 개선이다.

## 범위

- **전 화면 포함**: 사용자 화면 8개 라우트(dashboard·accounts·strategies·settings 등) + 인증/pending/rejected + admin 7개 라우트
- **기기 동등**: 모바일(390px)·데스크톱(1440px) 모두 동일 수준으로 검증·개선
- **테마 동등**: 라이트·다크 모두 검증

## 접근 방식: 감사 주도 (audit-driven)

추측이 아닌 실제 렌더링 증거를 기반으로 우선순위를 정한다. Phase 0의 감사 결과가 Phase 1~4의 구체 작업 항목을 확정한다.

## Phase 구조와 실행 모델 배정

각 Phase 태스크에는 비용·품질 균형 기준으로 가장 효율적인 모델을 명시한다.

| Phase | 내용 | 실행 모델 | 근거 |
|---|---|---|---|
| **0. 전 화면 감사** | 19개 라우트 × 모바일/데스크톱 × 라이트/다크 Playwright 스크린샷 → 문제 목록(심각도·카테고리 분류) 작성 | 캡처: **Haiku** / 분석: **Fable** | 캡처는 기계적 반복 작업, 문제 판별은 디자인 안목 필요 |
| **1. 일관성 정리** | 하드코딩 색·간격 → 토큰화, radius/shadow 편차 정리, Badge·EmptyState·Skeleton·page-header 패턴 통일 | 오케스트레이션: **Fable** / 병렬 수정: **Sonnet** | 기계적 다중 파일 수정은 Sonnet 병렬 투입이 비용 효율적 |
| **2. UX 흐름 개선** | 내비 정보구조(사이드바·바텀내비), 대시보드 정보 우선순위, 계좌→전략 이동 동선, 폼/스테퍼 UX, 로딩·빈·에러 상태 일관화, 터치 타깃 | 설계: **Fable** / 구현: **Sonnet** | UX 판단은 상위 모델, 확정된 설계의 구현은 Sonnet으로 충분 |
| **3. 비주얼 업그레이드** | frontend-design 가이드 적용: 페이지 로드 스태거 모션, Cormorant display 타이포 활용 확대, 배경 깊이(그라데이션·텍스처), 마이크로 인터랙션 | **Fable** 단독 | 미학적 창의 작업 — 모델 간 품질 편차가 가장 큰 영역 |
| **4. admin 동등화** | Phase 1~3에서 확립된 패턴을 admin 7개 라우트에 적용 | **Sonnet** 병렬 | 확립된 패턴의 반복 적용 |

### Phase 3 미학 지침 (frontend-design 스킬 발췌 적용)

- 명확한 미학적 방향에 전념: 기존 로즈골드 "럭셔리/refined" 톤을 심화 — 교체 금지
- 타이포: Cormorant Garamond display를 헤딩·수치 강조에 확대 적용, Pretendard 본문 유지
- 모션: 산발적 마이크로 인터랙션보다 페이지 로드 시 스태거 리빌(`animation-delay`) 등 고임팩트 순간에 집중, CSS 우선
- 배경·깊이: 단색 대신 그라데이션 메시·노이즈 텍스처·레이어드 투명도 등 컨텍스트에 맞는 깊이 표현
- 복잡도는 비전에 맞춤: refined 미니멀은 절제·정밀·간격/타이포 디테일로 승부

## 검증·커밋 규칙 (전 Phase 공통)

1. 각 Phase 완료 시 `npm run typecheck` 통과 확인
2. Playwright 스크린샷으로 실제 렌더링 확인 후 완료 선언 ("이론상 작동" 금지)
3. Phase 단위로 즉시 커밋 (여러 Phase 묶어서 커밋 금지)
4. `git push`는 사용자 명시 요청 시에만

## 제약

- **인증 화면 실스크린샷에는 로컬 kista-api 필요**: 실거래 백엔드이므로 에이전트가 임의 기동하지 않는다. Phase 0 시작 시 사용자가 API를 기동하거나, 불가 시 인증 화면은 코드 기반 감사로 대체한다.
- Docker가 3000 포트 점유 시 dev 서버는 3001 등으로 fallback — 실제 포트를 `/tmp/kista_dev.log`에서 확인한다.

## 비변경 원칙

- 로즈골드 브랜드 팔레트·Pretendard/Cormorant 폰트 스택 유지 (교체가 아닌 심화)
- 한국 증권 관례 색상 불변: `--pos` 빨강=상승/수익, `--neg` 파랑=하락/손실
- FSD 계층 규칙, 인라인 style 금지(CSS 토큰 예외), 싱글 쿼트·세미콜론 없음 등 기존 코딩 규칙 준수
- 포맷 무단 일괄 변경 금지

## 성공 기준

- Phase 0: 전 화면 문제 목록이 심각도·카테고리로 분류되어 문서화됨
- Phase 1: 감사에서 발견된 일관성 편차 항목이 모두 해소되고 하드코딩 스타일이 토큰으로 수렴
- Phase 2: 감사에서 발견된 UX 마찰 항목이 해소되고 로딩·빈·에러 상태가 전 화면에서 일관됨
- Phase 3: 모바일·데스크톱 × 라이트·다크 4개 조합 스크린샷에서 개선 전후 시각 품질 차이가 확인됨
- Phase 4: admin 화면이 사용자 화면과 동일한 패턴·품질 수준에 도달

# DCA 다중 규칙 화면 설계 (kista-ui)

- 작성일: 2026-10-21
- 선행 spec: kista-api `docs/superpowers/specs/2026-10-21-dca-multi-rule-ledger-design.md`(커밋 3c9a4953) §1·§3·§4.1·§6
- 상태: UX 설계 확정, **구현 보류**. kista-api 구현이 끝나 확정 계약(openapi diff)이 오면 `gen:types` 후 이 문서로 계획을 세운다. 필드 이름은 spec §6 초안 기준이라 바뀔 수 있다

## 1. 의도

DCA 전략 하나가 "종목 1개 + 규칙 1~10개(매수·매도 혼합)"가 된다. 지금 화면은 전략 = 규칙 1개를 전제로 한다(`DcaStrategyForm` + `DcaSettingsSection` + `DcaConditionsSection`, 상세·카드·이력도 단일 설정 요약). 이번 작업에서는 규칙 여러 개를 등록·수정·조회할 수 있게 바꾼다. 보유·평단 기준도 실잔고에서 전략 원장으로 바뀌므로 화면에 표시하는 기준도 함께 옮긴다.

대표 시나리오(spec §1): 업비트 ETH. 매일 09시 "평단 이하 AND RSI ≤ 30"이면 15,000원 매수(부족하면 거부), 매일 10시 "평단 +20% 이상"이면 50,000원 매도(부족하면 잔량 전부).

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 규칙 1~10개를 추가·수정·삭제할 수 있는 등록·수정 화면
- 상세·카드·회차 이력에서 규칙을 구분해서 보여 주기
- 원장 기준 보유·평단 표시(주식·크립토 공통)
- DCA를 통계·포트폴리오에 포함하고 관리자 수동 체결 보정을 연다. UI 쪽 제외 분기를 걷어낸다

**비목표**
- 규칙 이름(별칭) 필드. 규칙은 내용 요약으로 부른다(§3 결정 5)
- 실잔고 불러오기 버튼(§3 결정 6의 B안). 필요해지면 추가한다
- 보유 비율 프리셋 버튼(25/50/100%)
- 기존 단일 규칙 계약과 호환. API와 UI를 함께 배포한다(spec §6)

**실패 조건**
- 수정 저장 시 기존 규칙의 `ruleKey`를 잃거나 바꿔서 보낸다. 이렇게 되면 같은 날 같은 규칙이 다시 발동한다
- 보유 비율(HOLDING_PERCENT)을 매수 규칙에서 고를 수 있다
- 규칙 편집 화면이 PC 모달 위에 모달을 겹쳐 띄운다

## 3. 사용자 결정 사항 (2026-10-21 브레인스토밍)

| # | 항목 | 결정 |
|---|---|---|
| 1 | 규칙 편집 방식 | **요약 목록 + 규칙별 편집 화면**. 등록·수정 화면에는 규칙을 한 줄 요약으로 나열하고, 줄을 누르면 그 규칙 하나만 편집한다 |
| 2 | 방향 선택 시점 | 추가 버튼을 **"+ 매수 규칙 추가" / "+ 매도 규칙 추가"** 둘로 나눈다. 편집 화면은 방향이 정해진 채로 열리고, **저장한 규칙의 방향은 바꿀 수 없다**(방향이 바뀌면 다른 규칙인데 ruleKey가 유지되어 당일 중복 방지가 엉키는 것을 막는다). 바꾸려면 삭제 후 추가한다 |
| 3 | 부족 시 정책 기본값 | 매수·매도 모두 **PARTIAL**. 지금 동작과 같다 |
| 4 | 편집 화면 표시 위치 | **같은 화면 안에서 전환**. 전략 폼 자리에 규칙 편집 화면이 들어오고 "← 규칙 목록" / "완료" / "취소"로 돌아간다. PC 모달(인터셉팅 라우트)과 모바일 풀페이지가 같은 방식이고, 모달 위에 모달을 띄우지 않는다. 서버 저장은 전략 폼의 "등록/수정" 버튼을 누를 때 한 번만 한다 |
| 5 | 규칙을 부르는 이름 | 이름 필드 없이 **자동 요약**(예: "매수 · 매일 09시 · 15,000원")을 쓴다. 이력 항목의 ruleKey가 현재 규칙과 맞지 않으면 "삭제된 규칙 · 매수"로 표시한다 |
| 6 | 보유 시작값 | 등록 시 기존 **"중간부터 시작"(평단가·수량) 입력을 재사용**한다. 크립토는 소수 수량을 받고 기본값은 비워 둔다 |
| 7 | 편집 중 뒤로가기·닫기 | 규칙 편집 뷰에 들어갈 때 **브라우저 이력을 하나 쌓는다**. 모바일·브라우저 뒤로가기는 규칙 목록으로 돌아가고(편집 내용 폐기 = "취소"와 같음), 한 번 더 누르면 기존처럼 폼을 닫는다. PC 모달의 ESC·바깥 클릭은 지금처럼 폼 전체를 닫는다. 이탈 확인 다이얼로그는 두지 않는다 |

목업: `.superpowers/brainstorm/43021-1792589408/content/dca-rules-overview.html`(로컬 전용, gitignore 대상)

## 4. 화면별 설계

### 4.1 등록·수정 화면 (`features/strategy/create-strategy`)

목록 뷰(기본)는 위에서부터 다음 순서로 둔다.
1. 종목: 기존 `StrategyTickerSection`
2. 시작 예정일: 기존 `ScheduledStartSection`(등록 전용)
3. 보유 시작값: 등록 전용 선택 입력(평단가·수량). 크립토는 수량 소수(8자리), 주식은 정수
   - 수량과 평단가는 둘 다 넣거나 둘 다 비운다. 기존 공통 섹션과 같은 양방향 검증
   - 매도 규칙이나 평단(AVG_PRICE) 조건이 있는데 수량이 비어 있으면 안내 캡션 "보유 0에서 시작합니다. 이미 보유 중이면 입력하세요."를 표시한다
4. 규칙 (n/10)
   - 줄마다 방향 배지(기존 `directionBadgeClass`)와 요약 1행(주기·시점·규모), 2행(조건 AND 결합·부족 시 정책 라벨)을 표시하고 오른쪽에 `›`를 둔다. 줄 전체가 버튼이다
   - 하단에 "+ 매수 규칙 추가"와 "+ 매도 규칙 추가"(`brand-soft`, `sm`)를 둔다. 10개가 되면 둘 다 숨기거나 비활성화한다(빌더 재량)
   - 규칙이 0개면 빈 상태 문구 "규칙을 추가하세요."를 보여 주고 제출을 막는다
5. `FormActions`: "등록" 또는 "수정"

규칙 편집 뷰(전환)는 다음과 같다.
- 상단 "← 규칙 목록" 링크와 제목 "매수 규칙" 또는 "매도 규칙"(방향 배지 포함)
- 필드는 지금 `DcaSettingsSection`·`DcaConditionsSection`의 입력을 규칙 단위로 옮긴다. 순서는 다음과 같다
  1. 실행 시점: 주식은 MOO/MOC 카드, 크립토는 실행 시각 Select(KST 0~23시)
  2. 주기: 매일/매주/매월 + 요일·날짜. 기존 휴장일·말일 캡션을 유지한다
  3. 조건(AND, 최대 10개): 기존 조건 빌더와 풀이 문장을 그대로 쓴다
  4. 규모: 매도 규칙에만 "금액 / 보유 비율 %" 토글을 보여 준다. 매수는 금액만 쓴다. 금액 단위·최소값은 기존 규칙과 같다(주식 USD 소수 2자리, 크립토 원 단위 정수 5,000 이상). 비율은 0 초과 100 이하이고, 캡션은 "100% = 보유 전량"이다
  5. 부족 시 정책: `SelectionCard` 두 장. 기본값은 PARTIAL이다
     - 매수: 라벨 "원화가 부족할 때"(크립토) 또는 "달러가 부족할 때"(주식). 카드 "남은 금액만큼 매수" / "주문 안 함"
     - 매도: 라벨 "보유가 부족할 때". 카드 "잔량 전부 매도" / "주문 안 함"
- 하단에는 "취소"와 "완료"를 둔다. 기존 규칙을 편집할 때는 그 위나 아래에 `destructive` "규칙 삭제" 버튼을 둔다. 저장 전 초안이라 확인 다이얼로그는 두지 않는다
- "완료"를 누르면 규칙 단위 검증을 통과해야 목록에 반영된다. "취소"와 "← 규칙 목록"은 변경을 버린다
- 전환할 때 포커스는 편집 뷰 제목으로 옮기고, 돌아오면 해당 규칙 줄(새로 추가한 경우 새 줄)로 옮긴다
- 실행 시점·조건 캡션의 "평단가·보유 수량은 계좌 전체 보유 기준"은 원장 기준으로 문구를 바꾼다(예: "평단가·보유 수량은 이 전략 체결 기준")

계좌+종목 중복(spec §3: DCA도 계좌+종목당 1개로 되돌림)은 다른 전략과 같게 처리한다. 지금 등록 폼은 이미 전략이 있는 종목을 미리 걸러내지 않고, 서버 오류를 mutation 훅의 `onError` 토스트로 보여 준다. DCA도 이 방식을 따르고 별도의 사전 차단은 두지 않는다(설계자 판단). 예전의 "매수 DCA / 매도 DCA를 따로 등록" 전제가 남은 문구나 분기는 구현 단계에서 grep으로 찾아 정리한다.

수정 모드에서는 다음이 다르다.
- 종목은 읽기 전용이다(현행 유지). 규칙은 추가·삭제·편집할 수 있고, 저장 경로는 `PUT /dca-config`(`useReconfigureDcaMutation`)를 유지한다
- 기존 규칙은 `ruleKey`를 폼 상태에 보존해 그대로 다시 보내고, 새 규칙은 `ruleKey: null`로 보낸다
- 보유 시작값 입력은 등록 전용이다(다른 전략과 같다)

### 4.2 상세 화면 (`widgets/strategy-detail/DcaStrategyDetail`)

- 보유 현황: 크립토의 `CryptoHoldingGrid`(업비트 잔고 조회)를 걷어내고, 주식·크립토 모두 응답의 원장 `currentHoldings`·`avgPrice`로 표시한다. 평가금액·수익률은 현재가를 쓸 수 있으면 계산한다. 부제 "계좌 전체 보유 기준"은 원장 기준 문구로 바꾼다
- 순투입액·평가손익: 응답에 제공되면 표시한다(§6 질문 2)
- 규칙 카드: 규칙마다 방향 배지, 요약, 조건, "다음 {nextExecution}" · "최근 {lastExecution 결과}"를 보여 준다. 지금의 "추가 조건" 카드는 규칙 카드에 흡수한다
- 중지·재개·삭제·수정 진입은 현행을 유지한다

### 4.3 회차 이력 (`DcaExecutionHistory`)

- 각 항목에 방향 배지와 규칙 요약을 붙인다. 항목의 `ruleKey`를 현재 `rules[]`에서 찾아 요약을 만들고, 없으면 "삭제된 규칙"과 항목의 `direction` 배지를 표시한다
- 신규 skip 사유(`INSUFFICIENT_HOLDINGS`, 확정 시)의 라벨을 추가한다

### 4.4 전략 카드 (`widgets/strategy-card/DcaStrategyCard`)

- 단일 설정 요약을 "규칙 N개 · 매수 a · 매도 b"로 바꾼다. 다음 판정은 규칙들의 `nextExecution` 중 가장 이른 값, 최근 결과는 가장 최근 `lastExecution`으로 한다. 이 방식은 설계자 판단이다

### 4.5 통계·포트폴리오·관리자 보정

- DCA를 제외하던 UI 분기를 찾아 제거한다(예: `CyclePerformanceList`의 "코인 계좌는 DCA만 있어 사이클 성과가 없다" 분기, 포트폴리오·자산 개요의 DCA 제외). 전수 목록은 구현 단계에서 `grep -rn "DCA"`로 확정한다
- 관리자 수동 체결 보정(`widgets/admin-trade-list/AdminTradeCorrectionPanel`)에서 DCA 전략이 선택되고 제출되는지 확인한다. 지금은 서버가 400을 반환한다

### 4.6 공용 모델 (`entities/strategy`)

- 규칙 요약 포맷터(이름 예: `formatDcaRuleSummary`) 하나를 폼 목록·상세·카드·이력이 공유한다. 기존 `formatDcaSchedule`·`formatDcaCondition`을 조합한다
- 라벨은 `/api/meta`가 SSOT다: `DcaSizingType`, `DcaShortfallPolicy`. 단, 부족 시 정책 카드 문구는 방향별로 달라서(§4.1) 메타 라벨이 아닌 UI 문구로 둘 수 있다(빌더 재량)

## 5. 제약

- FSD: 폼은 `features/strategy/create-strategy`, 포맷터와 타입은 `entities/strategy`, 화면 합성은 `widgets/`
- 서버 상태를 `useState`에 복사하지 않는다. 규칙 초안은 RHF 폼 상태(사용자 입력)라 해당하지 않는다
- 카피 규칙(`docs/agents/constraints.md`)과 "크립토" 용어를 따른다
- 접근성: 규칙 줄은 버튼이고 accessible name에 요약을 포함한다. 뷰 전환 시 포커스를 이동한다. Select에는 `aria-label`을 단다
- 계약 확정 전에는 구현하지 않는다

## 6. kista-api에 확인할 것 (계약 확정 시)

1. 규칙별 `lastExecution`의 형태(상태·일시·skip 사유 포함 여부). 카드·상세의 "최근 결과" 표시에 쓴다
2. 전략 응답에 순투입액(통계 원금)과 평가손익이 포함되는지. 없으면 상세는 보유·평단·평가금액만 표시한다
3. 매도 REJECT 거부 사유를 신규 상수(`INSUFFICIENT_HOLDINGS`)로 할지, 메타에 라벨이 오는지
4. 크립토 전략의 `currentHoldings`가 원장 값(더는 null 아님)인지
5. 규칙 순서: 응답 `rules[]`가 입력 순서를 보존하는지(spec §4.1은 보존이라고 명시. 알림의 "규칙 순번"과 화면 순번을 맞추기 위해 확인)
6. 통계 응답에서 DCA의 형태: 사이클 성과 행(`CyclePerformanceList`)에 DCA가 의미 있는 값(원금 = 순투입액)으로 들어오는지, 크립토(KRW) DCA가 통계에 포함되는지. §4.5의 범위가 여기에 달려 있다. 포함되면 제외 분기를 지우고 원금 라벨을 "순투입액"으로 맞추고, 크립토가 제외되면 해당 분기를 유지한다

## 7. 빌더 재량

- 결정 7의 이력 쌓기 방식(`history.pushState` + `popstate`, 또는 쿼리 파라미터). 인터셉팅 라우트 모달의 `router.back()` 닫기(`dismiss='back'`)가 편집 뷰에서 쌓은 항목에 걸려 폼이 닫히지 않는 일이 없도록, "완료/취소"로 목록에 돌아갈 때 쌓은 항목을 정리해야 한다
- 규칙 편집 뷰의 폼 상태 구조. 예: 부모 RHF `useFieldArray` + 편집용 별도 `useForm` 초안, 또는 단일 폼 + 편집 인덱스. 단 "취소" 시 변경 폐기는 지켜야 한다
- 10개 도달 시 추가 버튼을 숨길지 비활성화할지
- 요약 문구의 세부 표기(구분자, 금액 축약)
- 파일 분할(`DcaRuleList`, `DcaRuleEditor` 등)과 기존 `DcaSettingsSection`·`DcaConditionsSection`을 재사용할지 재작성할지

### 사용 흔적 근거의 한계

- 운영 사용자는 2명이다(ACTIVE 2, PENDING·REJECTED 0, 마지막 가입 2026-06-18). "사용자 1명"은 미사용이 아니라 모수의 절반이다. 사용 흔적만으로 삭제를 권하지 않는다.
- 화면별 요청 수는 알 수 없다. kista-ui 컨테이너와 Caddy 둘 다 접근 로그를 남기지 않는다. 화면이 열렸다는 유일한 흔적은 `app_error_logs`의 `pathname`(30일 80건)이고, 오류가 난 화면만 잡힌다.
- 그래서 이 지침서의 삭제·축소 권고는 대부분 "제품 판단"이다. 화면 사용을 재려면 C6(접근 계측)이 먼저다.

## B. 보완이 필요한 것

### B1. 전략 상세가 빈 화면이 된다 — 02가 일부 해소, 나머지 보완

- 코드: `widgets/strategy-detail/StrategyDetailContent.tsx:45`의 `if (!account || !strategy) return null`. 다른 탭에서 전략을 지웠거나 목록 쿼리가 갱신돼 항목이 사라지면 헤더도 없는 빈 화면이 남는다.
- 02 태스크 6이 `useSuspenseQuery`로 `return null`을 없앤다. 남는 것: 단건 조회(api T11)가 404를 줄 때의 화면. "삭제된 전략입니다" + 계좌 상세로 가는 링크를 `not-found`로 통일한다. 계좌 상세도 같다.
- 결정 불필요. 02 태스크 6의 완료 판정에 "삭제된 리소스 URL을 열면 안내 화면이 뜬다"를 더한다.

### B2. 조건이 안 맞는 동작 버튼이 숨겨진다 — 05에 규칙 추가

- 코드: 투자금 추가·인출은 사이클 미진행·VR·잔액 0이면 렌더되지 않는다(`StrategyDetailContent.tsx:66-76`). 사용자는 버튼이 왜 없는지 알 수 없다.
- 05 4절이 `blockedActions[{action, reasonCode}]`를 받는다. 규칙을 못 박는다: **그 종류의 전략이 지원하는 동작은 항상 보이고, 지금 못 하면 비활성 + 사유를 보인다. 그 종류가 아예 지원하지 않는 동작만 숨긴다.**
- api 확인(2026-11-13, U3): T6가 구분한다. `allowedActions ∪ blockedActions`가 그 종류가 지원하는 동작 전체이고, 둘 다에 없으면 미지원이다. `blockedActions`에는 `reasonCode`가 반드시 있다. UI는 합집합을 버튼으로 그리고 `blockedActions`에 든 것만 비활성 + 사유로 보인다.

### B3. 승인 대기 안내 문구가 삭제될 증권사를 가리킨다

- 코드: `app/pending/page.tsx:16` "KIS API 자격증명 입력". KIS는 삭제가 결정됐다.
- 05 태스크 9의 완료 판정 grep(`'KIS'`)은 따옴표 리터럴만 잡아 이 문구를 놓친다. 판정에 `grep -rn "KIS" app/pending`을 더하고 문구를 "증권사·거래소 계좌 연결"로 바꾼다.
- 결정 불필요.

### B4. 반려 화면의 "반려 사유" 카드가 사유를 보여주지 않는다

- 코드: `app/rejected/page.tsx:23-36`. 제목은 "반려 사유"인데 본문은 고정 문구다. 생성 타입에는 `rejectReason`이 있다(`shared/lib/api-types.ts:4366`).
- 경위(2026-11-13 정정): 2026-07-12 설계 초안(`59d490f1`, 양 레포 연계)이 있었고, **서버 쪽은 구현돼 있다** — `UserResponse.rejectReason`, 관리자 반려 요청의 `reason`, 텔레그램 반려 알림의 사유 줄, `users.reject_reason` 컬럼(fable-api 확인). UI 쪽만 구현되지 않았다: 관리자 반려 버튼은 사유를 묻지 않고(`features/admin/approve-reject`에 `reason` 0건), 반려 화면은 필드를 읽지 않는다.

## C. 추가가 필요한 것

전부 신규 기능이다. 승인 전에는 만들지 않는다.

### C1. 내보내기(CSV)

- 코드: 0건.
- 제품 판단: 가계부를 2명이 804건·1,056건 입력했다. 이 데이터를 앱 밖으로 꺼낼 방법이 없다. 연말 정산·다른 도구로의 이전·백업을 하려는 사용자를 풀어준다. 체결 내역 내보내기는 증권사가 이미 제공하므로 순위가 낮다.
- api 필요: 페이지형 목록은 UI가 전량을 갖지 않으므로 서버가 `text/csv`를 준다(같은 필터 파라미터).
- 대상 후보: 가계부 거래, 자산 기록. 그다음 사이클 성과.

### C2. 가계부 가져오기(CSV)

- 제품 판단: 거래 804건을 손으로 입력했다. 카드·은행 내역 CSV를 올려 미리보기 후 등록하면 입력 부담이 준다. 새 사용자가 가계부를 시작하는 문턱을 낮춘다.
- 비용이 크다: 열 대응, 중복 판정, 카테고리 추론이 전부 서버 일이다(api 필요). 일괄 등록 미리보기(api 지침서 10의 2-6절)와 같은 "미리보기 → 확정" 모양으로 맞춘다.
- 권고: C1보다 뒤. 사용자가 실제로 원하는지 먼저 묻는다.

### C3. 삭제 직후 실행 취소

- 코드: 삭제는 전부 확인 다이얼로그 뒤 즉시 실행이다. 서버는 이미 soft delete다(사용 흔적: `deleted_at`이 있는 행이 거래 88, 자산 202, 재무계좌 4, 카테고리 11).
- 제품 판단: 가계부처럼 자주 지우고 다시 쓰는 목록에서 확인 다이얼로그는 매번 멈추게 하고, 잘못 지운 것은 되살리지 못한다. "삭제했습니다 · 실행 취소" 토스트가 둘을 함께 푼다. 06의 `ConfirmDialog` 기준("되돌릴 수 없는 동작과 돈이 움직이는 동작에만 확인")과 맞물린다. 되돌릴 수 있게 되면 가계부 삭제는 확인이 필요 없다.
- api 필요: 복구 엔드포인트(`POST …/{id}/restore`). 대상은 가계부 5종. 매매 쪽(전략·계좌 삭제)은 대상이 아니다.

- **사용 근거 없이 지운다.** A3·A4는 사용자 2명 중 누가 보는지 모른다. 사용자 답 없이 지우지 않는다.
- **A1은 내비 구조를 바꾼다.** 하단 탭 6개가 5개가 되면 모바일 배치가 달라진다. 06 9절(내비 항목 배열 단일화) 뒤에 한다.

- **C5는 실계좌 주문을 낸다.** 만들면 Opus + `/code-review high`.

## 하지 말아야 할 것

- 이 지침서의 A·C 항목을 승인 없이 실행하지 않는다.
- 사용 흔적이 0이라는 이유만으로 지우지 않는다. 모수가 2명이다.
- 대칭을 맞추려고 쓸모없는 동작을 만들지 않는다(재무계좌 복제 등). 대칭은 같은 종류의 리소스에서 사용자가 기대하는 동작에만 맞춘다.
- 신규 기능을 UI만으로 흉내 내지 않는다(전량을 받아 브라우저에서 CSV 생성, `localStorage`로 삭제 취소 등). 책임 분담 원칙(05)대로 서버가 한다.
- 재심에서 유지한 결정(빗썸, 대시보드 KPI)을 다시 제안하지 않는다.

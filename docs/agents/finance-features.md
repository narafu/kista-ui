# 가계부(finance) — features

공통 도메인 규칙은 docs/agents/finance.md

## features

- **`asset/save-asset`**: `AssetForm`이 `mode: 'create' | 'edit' | 'duplicate'` 하나로 3형태를 처리한다(네이티브 `useState` + `<form onSubmit>`, RHF+zod 아님 — strategy 도메인 전용 패턴). 카테고리(`categoryId`)·계좌(`accountId`)·자산군(`assetClass`)·시장(`market`)은 각각 독립 `Select`다(연쇄 리셋 없음). `assetClass`/`market` 기본값은 각각 `'CASH'`/`'DOMESTIC'`으로 고정해 사용자가 직접 고르게 한다. 로컬 `ComboField`(자유 입력 `Input` + 추천 `Select`)는 이제 `strategy`(운용전략 자유 메모) 한 곳에만 쓰이고, 추천 목록은 `@entities/user`의 `useMeQuery().data.strategySuggestions`(유저별 설정)에서 가져온다 — `@entities/finance`는 다른 entity를 import할 수 없어(entities 간 cross-import 금지) 두 entity를 조합하는 지점이 이 feature다. 카테고리 Select는 `@entities/finance`의 `getCascadeLevels`/`getCategoryPath` 기반 계단식 Select다 — depth 무관하게 동작하도록 설계돼 트리가 2단을 넘어 깊어져도 이 컴포넌트는 수정할 필요가 없다. `selectedPath: string[]` 상태 하나로 각 단의 선택값을 담고, edit/duplicate 모드는 `getCategoryPath`로 기존 `categoryId`에서 경로를 역산해 복원한다. 계좌는 선택(nullable), asset class/market 라벨은 `@entities/meta`의 `useMeta().meta.assetClasses`/`markets`에서 가져온다. 운용전략 필드는 L1이 '투자'(`isInvestmentCategoryId`)일 때만 화면에 노출된다 — 단 payload의 `strategy`는 항상 현재 상태값을 그대로 전송한다(카테고리 무관 자유 필드라는 구 설계 그대로, 비노출이 곧 서버 제출값 삭제를 의미하지 않는다). 값이 지워지는 시점은 사용자가 L1 Select를 '투자'가 아닌 값으로 능동적으로 바꿀 때뿐 — edit 모드 진입 시 레거시 기록(비-투자 카테고리에 저장된 기존 strategy 값)을 복원하는 경로는 건드리지 않아 데이터가 조용히 유실되지 않는다
- **`finance/save-transaction`**: 수입/소비/저축 탭의 거래내역 CRUD. `TransactionFormDialog`(create/edit 겸용, `AssetForm`과 동일하게 네이티브 `useState`+계단식 카테고리 Select)는 **라우트가 아니라 다이얼로그**다 — 거래내역 단건 GET이 없어 라우트 진입 시 id만으로 조회가 불가능하고, 목록 캐시에 이미 데이터가 있는 다이얼로그가 더 단순하기 때문. `NewTransactionButton`은 `NewAssetButton`(라우트 이동)과 달리 자체 `open` state로 다이얼로그를 열고 닫는 완전히 자기 완결적인 컴포넌트다 — **다이얼로그는 `open && <TransactionFormDialog .../>`처럼 조건부로만 마운트한다**(상시 마운트하면 내부 `useState`가 다음 열림에도 초기화되지 않고 이전 입력값이 남는다, `CategoryManager`의 `formTarget` 패턴과 동일 이유). `TransactionFormDialog`의 `windowFrom`/`windowTo` prop은 호출부에 따라 의미가 다르다 — 등록은 "오늘 기준" 독립 창(하한 없음, 상한은 이번 달 말일 — 과거 연도 등록도 허용), 수정은 "지금 조회 중인" 12개월 창(자세한 이유는 `TransactionFormDialog` 주석 참고). 삭제 확인은 `finance/delete-transaction`이 아니라 `shared/ui/ConfirmDeleteDialog`(제목·설명 문구만 받는 범용 삭제 확인 다이얼로그)를 직접 쓴다
- **`finance/manage-budgets`**: 예산 CRUD. Dialog가 아니라 인터셉팅 라우트다 — 목록 `/finance/budgets/[type]`(진입: `FinanceHeader` "예산 관리" 링크), 추가 `/new`(`?duplicateFrom=` 복제, `?categoryId=` 카테고리 프리필 — `FinanceBudgetProgress` "예산 미설정 → 예산 추가" 링크가 이걸로 폼 직행), 수정 `/[id]/edit`. 일반 페이지와 `@modal` 버전이 `app/(main)/finance/budgets/[type]/**/XxxBody.tsx`를 공유하고, Body가 카테고리·예산 목록을 서버에서 조회해 하이드레이션하며 수정·복제 원본을 prop으로 넘긴다(예산 단건 GET 없음 — 목록에서 찾음, 다른 type 예산 id면 404). `BudgetForm`은 `dismiss`(`push`→목록 이동 / `back`→`router.back()`)로 종료를 분기하고 제목은 Body의 `PageHeader`가 맡는다. `BudgetManager`는 `type: FlowType` prop을 받고 필터·페이지를 URL에 보존한다(`docs/agents/app.md` 인터셉팅 라우트 항목). 예산은 EXPENSE·SAVING뿐 아니라 INCOME 카테고리에도 걸 수 있다(ASSET만 kista-api가 400). 카테고리 기간 중첩(`finance_budgets_no_overlap`) 위반은 409로 오고 `useCreateFinanceBudgetMutation`/`useUpdateFinanceBudgetMutation`이 서버 메시지를 그대로 toast로 노출한다(별도 문구 분기 불필요)
- **`finance/manage-strategy-suggestions`**: 자산 등록 폼 추천 목록 — 유저별 설정(`user_settings.strategy_suggestions`, `PUT /api/settings/strategy-suggestions`)이라 ADMIN 게이트 없이 모든 로그인 유저에게 노출된다. `/finance` 설정 탭(계좌관리 아래) 위치는 유지 — 자산 등록 폼 전용 값이라 일반 계정 설정(`/settings`)보다 finance 도메인에 두는 게 자연스럽다는 판단. 값은 `@entities/user`의 `useMeQuery().data.strategySuggestions`, 저장은 `useUpdateStrategySuggestionsMutation`이 `{suggestions}`만 PUT한다(엔드포인트가 이 필드 하나만 받는 부분 갱신). `SuggestionListEditor`(`shared/ui`) 조작마다 즉시 반영하는 UX는 유지
- **`finance/manage-categories`**: `/finance` 설정 탭의 카테고리 CRUD. `CategoryManager`가 4타입(ASSET/INCOME/EXPENSE/SAVING) 세그먼트(`shared/ui/SegmentedToggle`, 가계부 탭바 `SectionTabBar`와 같은 시각 패턴)를 소유하고 `useFinanceCategoriesQuery(type)` 트리를 L1+`children` 들여쓰기로 렌더한다. 생성/수정은 `CategoryFormDialog`(Base UI `Dialog`) 하나가 겸용 — 수정 모드는 PUT이 `parentId`/`type`을 무시하는 서버 제약 때문에 이름·정렬순서만 노출한다. 트리 행(`CategoryRow`, 재귀)은 별도 파일로 추출돼 있고 `lockSystemCategories?: boolean`(기본 `true`)를 받는다 — 시스템 카테고리(`system:true`)는 기본적으로 수정·삭제 버튼을 비활성화한다(`shared/ui/ShareableRowActions`의 `locked` — `IconButton` native `disabled` + 흐림). 삭제 확인(`DeleteCategoryDialog`)은 `collectSubtreeIds`로 하위 개수를 세어 "하위 N개 카테고리가 함께 삭제됩니다" 문구를 만든다
  - **관리자용 시스템 카테고리**: `/admin/settings` 페이지에 배치된 `SystemCategoryManager`/`SystemCategoryFormDialog`(같은 슬라이스, `SystemCategoryManager`만 export)는 `/api/admin/finance/categories`(`app/api/admin/[[...path]]` catch-all 프록시, ADMIN role은 kista-api가 검증)를 소비해 `groupId=null`·`system:true`로 고정되는 공통 카테고리를 관리한다. 그룹 스코프 카테고리와 시나리오·권한·데이터소스가 달라 훅을 조건 분기하지 않고 완전히 별도 컴포넌트로 분리했다(`useSystemFinanceCategoriesQuery`/`useCreateSystemFinanceCategoryMutation` 등, 캐시 루트도 `financeKeys.systemCategoriesRoot()`로 분리). `CategoryRow`에 `lockSystemCategories={false}`를 넘겨 시스템 카테고리도 수정·삭제 가능하게 한다(이 화면 자체가 시스템 카테고리 관리 화면이므로 기본 잠금을 반전)
- **`finance/manage-accounts`**: `/finance` 설정 탭의 재무 계좌(은행/증권사/보험/거래소) CRUD — `entities/account`(한국투자증권 브로커 계좌)와는 다른 도메인이라 디렉토리·import를 절대 섞지 않는다. `AccountManager`가 목록에서 `accountNo`를 `maskAccountNo`(뒷 4자리만 노출)로 마스킹해 렌더하고, 수정 다이얼로그에서만 전체 값을 편집한다. 목록 상단 계좌타입 필터·정렬(이름/유형/등록순) Select는 계좌 수가 적어 서버 API 없이 클라이언트 `useMemo`로 처리한다. 계좌도 공유/귀속 대상이다(`useShareFinanceAccountMutation`/`useUnshareFinanceAccountMutation`) — 단 flat 목록이라도 unshare는 소유자 아닌 그룹 멤버도 실행 가능해(caller의 group-scope 목록에서 항목이 사라져야 함) create/update와 달리 `upsertById`가 아니라 다른 finance 리소스와 동일하게 `accountsRoot()` invalidate 방식을 쓴다. 계좌번호는 서버가 신규/수정 요청에 숫자만 허용(`@Pattern`, 기존 DB 데이터는 마이그레이션하지 않음) — `AccountFormDialog`가 입력 시 `digitsOnly`로 즉시 strip하고, 수정 모드 초기값도 `digitsOnly`로 정규화해 비숫자 legacy 값을 건드리지 않고 다른 필드만 고쳐도 400을 맞지 않게 한다
- **`finance/manage-group`**: `/finance` 설정 탭의 그룹 멤버·초대. kista-api는 **1인 1그룹 정책**(개인 그룹 자동생성 없음)이라 `useFinanceGroupsQuery()`는 0개(무그룹=개인) 또는 1개(그룹 소속)만 반환하고 `FinanceGroup`에 `personal`·`name` 필드가 없다 — "그룹 소속 여부"(`groups.length`) 자체로 개인/그룹을 판정한다. `GroupManager`가 `groups`를 한 번만 구독하고, 그룹이 있으면 `GroupSection`(멤버 목록+탈퇴)을 렌더하며 없으면 초대 발급 안내만 보여준다 — 자식이 같은 쿼리를 다시 구독하지 않는다. **무그룹 유저가 초대를 발급하는 시점에 kista-api가 그 자리에서 새 그룹을 만들고 본인을 OWNER로 등록한다**(`POST /groups/{id}/invitations`의 path `id`는 이 경우 서버가 무시 — `GroupManager`가 무그룹일 때 `InviteDialog`에 `me.id`를 자리채움 값으로 넘긴다). 발급·수락·탈퇴·추방 mutation의 `financeKeys.all` 무효화는 위 그룹 스코프 항목 참고. 그룹 탈퇴·추방 시 데이터의 `group_id`는 **이관되지 않는다**(kista-api `leaveGroup`) — 탈퇴자는 더 이상 조회할 수 없고 남은 멤버는 계속 조회하므로, 안내 문구는 "더 이상 접근 불가"다. OWNER가 나가면 서버가 남은 멤버 중 가장 먼저 가입한 사람을 자동 승계한다. 1인 1그룹 정책상 이미 그룹에 소속된 유저는 다른 그룹 초대를 수락할 수 없어(서버가 거부) `AcceptInvitationForm`은 무그룹일 때만 노출한다. `isOwner` 게이팅은 `GroupSection`이 멤버 목록에서 내 role을 찾아 판정하고, 발급된 코드는 재조회가 안 되므로 다이얼로그가 열려 있는 동안만 표시하고 복사 버튼+경고 문구를 둔다. `AcceptInvitationForm`은 코드 입력 후 수락만 처리한다(코드를 본인이 직접 입력하는 흐름이라 거절 버튼 없음).
- **`finance/save-transaction`·`finance/manage-budgets` 그룹 공유 전환**: 개인 소유(`groupId` 없음) 거래내역·예산을 소유자의 현재 그룹으로 전환하는 `PATCH .../{id}/share`가 있다(`useShareFinanceTransactionMutation`/`useShareFinanceBudgetMutation`, 성공 시 각각 `transactionsRoot()`/`budgetsRoot()` 무효화). 역방향 `PATCH .../{id}/unshare`(`useUnshareFinanceTransactionMutation`/`useUnshareFinanceBudgetMutation`)도 있다 — 소유자 한정이 아니라 같은 그룹 멤버면 누구든 개인 소유로 되돌릴 수 있고, 되돌린 뒤 `userId`는 실행자가 아니라 기존 소유자 그대로 유지되며 이미 개인 소유면 멱등 200이다. 자산 스냅샷도 동일 패턴이다(`useShareAssetSnapshotMutation`/`useUnshareAssetSnapshotMutation`, `AssetSnapshotResponse.groupId`). `widgets/finance-record-list`·`widgets/asset-record-list`의 복제 버튼 옆, `manage-budgets/BudgetManager`의 수정 버튼 옆에 그룹 소속(`useFinanceGroupsQuery().length > 0`, `useCanShareToGroup()`) 상태에서 소유 형태에 따라 "공유"(`!item.groupId`) 또는 "귀속"(`item.groupId` 있음, 그룹 소유를 개인으로 되돌리는 버튼) 버튼 하나만 노출한다 — 무그룹 상태에서는 둘 다 없다. account는 `manage-accounts` 항목 참고. category는 트리 구조라 `PATCH .../{id}/share`·`.../unshare`가 대상 노드 하위 전체(임의 depth)를 cascade로 함께 전환한다(kista-api recursive CTE 벌크 UPDATE). `useShareFinanceCategoryMutation`/`useUnshareFinanceCategoryMutation`(`entities/finance`)이 `categoriesRoot()` 무효화 방식(다른 category 뮤테이션과 동일 패턴)을 쓴다. `manage-categories/CategoryRow`가 `canShare`/`onShare`/`onUnshare` prop을 재귀로 하위까지 전달해 각 행이 자신의(서버가 이미 cascade 반영한) `groupId`를 그대로 렌더한다 — system 카테고리(`category.system`)는 그룹 개념이 없어 버튼 자체가 렌더되지 않는다. `SystemCategoryManager`는 이 prop들을 넘기지 않아 관리자 화면엔 노출되지 않는다. **신규 생성도 `POST /{resource}?shareToGroup=true` 한 번으로 그룹 소유로 원자적으로 만든다** (5개 리소스 공통). 대상 그룹은 서버가 `userId`로 해석하므로 클라가 groupId를 보내지 않는다. `BudgetForm`/`TransactionFormDialog`/`CategoryFormDialog`의 생성 모드와 `AssetForm`의 생성/복제 모드(`mode!=='edit'`), `AccountFormDialog` 생성 모드에 "그룹으로 저장" 스위치가 있다 — `useCanShareToGroup()`으로 게이팅, 기본값 켜짐, 체크 시 `useCreateXxxMutation` variables에 `shareToGroup: true`를 얹으면 `createXxx(data, { shareToGroup })` 단일 호출로 끝난다(부분 실패 상태 없음). 예산 그룹 기간 겹침(EXCLUDE 409)은 create 자체가 실패로 반환한다(`onError` → `apiMsg` 토스트); 개인 스코프 겹침은 서버가 규칙대로 자동 트림/삭제한다. **카테고리는 계층이라 부모가 개인 소유면 서버가 400** — `CategoryFormDialog`가 선택된 부모의 `groupId` 유무(`getCategoryPath(l1Categories, parentId).at(-1)`)로 토글을 게이팅해, 개인 부모 아래에서는 토글을 숨기고 "개인 카테고리 하위에는 그룹 공유 카테고리를 만들 수 없습니다" 안내를 띄운다. `widgets/finance-bulk-register`(일괄 등록)도 같은 `?shareToGroup=true`로 서버가 각 항목을 그룹 소유로 생성하며(항목별 실패는 응답 `failures[]`), 기본값도 단건 폼과 동일하게 그룹 소속이면 켜짐(`useState(true)`)이다.

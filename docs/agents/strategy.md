# 전략·DCA·브로커 분기(strategy) — 필요시 Read

entities/features/widgets에 흩어져 있던 전략·DCA·브로커 서술을 원 출처별 절로 모은 문서다.

## entities

- **TradingCycleResponse 필드 추가 시**: `entities/strategy/model/types.ts` + `entities/strategy/api/index.ts`의 `normalizeStrategy()`를 함께 수정
- **`divisionCount`**: INFINITE 전략 전용 분할 수 (20/30/40). VR/PRIVACY는 `undefined`로 정규화된다
- **`vr`**: VR 전략 전용 요약 `{ value, bandWidth, intervalWeeks, recurringAmount, poolLimit, gradient }`. 비VR은 없음
- **`isReverseMode`**: 리버스모드 활성 여부. `StrategyRequest`에는 없음
- **`StrategyRequest`**: VR 등록 시 `initialDeposit`, `intervalWeeks`, `bandWidth`, `recurringAmount`를 포함한다. 적립식 VR은 `initialDeposit=0` payload를 허용한다. `initialHoldings`/`initialAvgPrice`(중간부터 시작)·`scheduledStartDate`(시작예정일)는 세 전략 공통·등록 전용 필드다 — features의 해당 항목 참고
- **`Strategy.startDate`**: 응답의 사이클 시작(예정)일(yyyy-MM-dd). `startDate > todayKst()`면 아직 매매 시작 전 — `isScheduledStart(strategy)`로 판정하고 `scheduledStartBadgeLabel(startDate)`로 "N월 N일 시작예정" 배지 라벨을 만든다(둘 다 `entities/strategy` export, `fmtMonthDay`는 ko-KR에서 "8. 1." 형식이라 이 문구엔 쓰지 않음)
- **strategy**: 백엔드 이름은 `TradingCycle`. pause/resume은 strategyId 기준. capability는 `StrategyTypeMeta` 필드를 직접 소비하고, 최소 시드·기준가·가용 예수금은 서버 검증(`useStrategyValidationQuery`)의 `derived`를 쓴다. `seedBadgeClass()`를 재사용한다
- **strategy DCA**: 타입은 `entities/strategy/model/types.ts`. 라벨(주기·지표·연산자·skip 사유·방향)은 메타 `labelOf`가 SSOT이고 요일명만 로컬 상수(`WEEKDAY_LABEL`, java DayOfWeek)다. 주문 유형도 메타 `labelOf('orderTypes')`("MOC(종가시장가)" 형식)를 쓴다. `MetaProvider.labelOf`는 누락된 메타 키를 가드한다(1h 메타 캐시가 새 키보다 오래됐을 수 있음). 한 전략이 `rules[]`(규칙별 `ruleKey`·`direction`·`sizing`·`shortfall`)를 갖고, 보유 수량·평단은 원장 값 `currentHoldings`·`avgPrice`다(`StrategyDcaSummary`). 실행 이력 `DcaExecution`은 `ruleKey`·`direction`을 갖는다. 메타 키 `dcaSizingTypes`·`dcaShortfallPolicies`가 금액 방식·부족 시 정책 라벨/선택지의 SSOT다. `useDcaExecutionsQuery`는 `placeholderData`로 이전 페이지를 유지한다. 실행 이력(`DcaExecutionHistory`)은 기간·방향·규칙 필터와 페이지 크기 선택을 서버 필터(`from`·`to`·`direction`·`ruleKey`, `DcaExecutionFilters`)로 보낸다. 런타임 설정 `strategies.DCA`는 기본 enabled=false이며 관리자 폼은 DCA 키 누락을 가드한다
- **DCA 금액**: 규칙의 금액은 `sizing`(방식+값)이고 금액 계열 필드는 `amount`(계좌 통화)다. 구 필드 `amountUsd`는 제거됐다(요청·응답 모두)

## features

- **`create-account/steps/BrokerStep`**: TOSS / MERITZ / MOCK 선택. `BrokerCode`는 `@shared/lib/api-schema`. `BROKER_UI`에 없는 코드는 카드가 렌더되지 않으므로(`return null`) 신규 브로커 추가 시 반드시 항목 추가 필요
- **`create-account/steps/ApiStep`**: 모든 broker는 `useTestBrokerConnectionMutation` 연결 테스트 통과가 다음 단계 조건이다. 거래소 오류 코드 문구는 `@entities/account`의 `brokerErrorMessage`. MERITZ는 계좌번호 없이 App Key에 묶인 계좌 하나로 매매하므로 계좌마다 키를 따로 발급하라는 안내를 띄운다. MOCK은 이 스텝 자체를 거치지 않음
- **`create-account/steps/AccountInfoStep`**: TOSS만 계좌번호 형식(`ACCOUNT_CONFIG`)이 있다. `ACCOUNT_CONFIG`에 없는 broker(MOCK, MERITZ)는 계좌번호 입력 없이 별칭만 입력. 앱키에 계좌가 묶인 broker(MERITZ)는 `isKeyOnlyBroker`가 기준이다
- **`strategy/create-strategy`**: 다이얼로그/드로어 없이 전용 라우트로 등록·수정한다 — `app/(main)/accounts/[id]/strategies/new`(등록), `.../strategies/[sid]/edit`(수정). `StrategyFormPage`가 `initial` prop 유무로 create/edit을 분기한다. 폼 내부는 반응형 분기 없이 모바일·PC 동일한 1열 레이아웃을 사용한다(`VrSettingsSection` 등).
- **`strategy/create-strategy` 전략 목록 진입점**: `/strategies` 헤더의 `AddStrategyButton`은 계좌 0개면 숨김(빈 상태가 계좌 등록 안내), 1개면 `NewStrategyButton`으로 바로 이동, 2개 이상이면 Popover로 계좌를 고른 뒤 같은 `/accounts/{id}/strategies/new` 라우트로 보낸다 — 폼 안에서 계좌를 바꾸는 방식은 폼 전체가 accountId 기반 조회(증권사·예수금·현재가·시드 미리보기)를 전제해 채택하지 않았다
- **`strategy/create-strategy` DCA 분기**: `StrategyForm`은 유형 선택을 유지하고, 유형이 DCA(등록) 또는 `initial.type === 'DCA'`(수정)면 별도 `DcaStrategyForm`(자체 RHF + zod `dcaFormSchema`, `buildDcaPayload`)을 렌더한다 — `useStrategyForm`의 submit guard가 시드·예수금·VR에 묶여 있어 재사용하지 않았다. 폼은 규칙 목록 + 같은 화면 규칙 편집 뷰(`rules[]`)이며, 편집 뷰마다 `shared/lib/subviewHistory`로 고유 토큰을 단 이력 항목을 하나 쌓아 브라우저 뒤로가기가 목록 뷰로 돌아오게 한다. 등록의 유형 선택은 `header` prop으로 넘겨 목록 뷰에만 렌더한다 — 편집 뷰에서 유형을 바꾸면 폼이 언마운트되며 편집 이력 칸만 남아 ESC가 두 번 필요했다. 수정은 `PUT /dca-config`(`useReconfigureDcaMutation`)로 저장하며 종목만 읽기 전용이다(방향은 규칙별 고정). 보유 시작값·예수금(`initialDeposit` → payload `initialDeposit`, 계좌 통화·0 이상·비우면 생략=0)은 등록 전용이다. DCA는 원장 예수금·보유 안에서만 매수·매도한다(서버가 실잔고를 보지 않음). 예수금 입력은 다른 전략과 같은 `SeedInputSection`(`currency` prop으로 계좌 통화)이고, 등록 때만 등록 검증(바디 = `buildDcaCreatePayload`, 못 만들면 검증 생략)의 `derived.availableCash`를 가용 예수금 참고값·비율 채우기로 쓴다(초과해도 경고만, `minSeed` 없음). 지금 입력에 대한 서버 거절은 등록 버튼 위에 보이고 등록하지 않는다(`aria-live="polite"`로 알리고 누르면 그 사유로 포커스, 규칙이 없을 때는 서버의 빈 규칙 거절을 숨긴다 — VR 재설정도 같은 방식으로 확인 다이얼로그를 열지 않고 사유로 포커스). `useStrategyForm`의 검증은 DCA에서 꺼 둔다(DCA 폼이 따로 부른다). "말일" = `dayOfMonth: null`. DCA는 등록 후 `todayOpenBatchMissed` 토스트도 띄우지 않는다. `useStrategyFormData`의 `enabledStrategyTypes`는 계좌 시장의 티커를 쓸 수 있는 유형만 남긴다. DCA 규칙 편집은 메타 주문 유형 중 MOO·MOC만 보이고 스키마도 둘만 받는다
- **`strategy/adjust-capital`**(`CapitalForm kind='inject'|'withdraw'` — 추가·인출은 요청 필드·문구·한도만 다른 한 폼): 투자금 추가는 PRIVACY·INFINITE·DCA 진행 중 사이클에 예수금을 추가한다(주식 편입 입력은 2026-11 제거 — VR 재설정의 투자금 추가는 주식 편입 유지)(`POST /api/trading-cycles/{id}/capital-injection`, `useInjectCapitalMutation`). 같은 사이클을 유지하고 다음 거래일 주문부터 반영되며(INFINITE: 1회 매수금↑·T 앞당김, PRIVACY: 배수 재계산) 이번 사이클 수익률에서는 추가분이 빠진다. 스키마 오류는 입력칸 아래에 표시한다. 금액 단위·자릿수·표기는 계좌 통화(`currency` prop — 전략 상세가 계좌 broker로 정함, KRW 정수·USD 소수 2자리)이고, DCA는 반영 시점을 "다음 회차"로 쓰고 효과 문구를 두지 않는다. 진입은 전략 상세 헤더의 "투자금 추가" 버튼이고(활성 여부는 전략 응답 `allowedActions`/`blockedActions`(`actionState`)가 결정 — allowed=활성, blocked=비활성+메타 `strategyActionBlockReasons` 사유, 둘 다 없음=숨김) `FormDialog`로 그 자리에서 연다. 제출 후 AlertDialog 확인이 다이얼로그 안에 한 번 더 뜬다. 성공 시 `orderKeys.preview`와 잔고 이력·성과(`tradeKeys.all`·`statsKeys.all`)를 무효화한다 — 잔고 이력은 staleTime 5분이라 빠뜨리면 추가 결과가 바로 안 보인다(인출·reconfigure-vr도 같다).
- 투자금 인출(`kind='withdraw'`): 같은 대상(PRIVACY·INFINITE·DCA 진행 중 사이클)에서 예수금을 계좌 통화로 인출한다(`POST /api/trading-cycles/{id}/capital-withdrawal` `{amount}`, `useWithdrawCapitalMutation`). 실제 계좌 출금은 증권사에서 직접 해야 한다. 한도는 `Strategy.ledgerDeposit`(장부 예수금, 계좌 통화) 이하로 폼에서 검증하지만 서버가 미체결 매수 주문분을 더 차감해 400으로 거절할 수 있다(상한일 뿐). 진입은 상세 헤더의 "투자금 인출" 버튼(추가와 같은 `FormDialog` 하나, 활성·숨김도 `allowedActions`/`blockedActions`로 같은 규칙), 성공 시 추가와 같은 키를 무효화한다. 폼 안내는 투자금 추가처럼 반영 시점 문장만 둔다.
- **`strategy/create-strategy`**: 수정 모드는 기본적으로 시작금액(`initialDeposit`) 읽기 전용이며, `currentHoldings === 0`일 때만 등록과 같은 시드 입력 UI를 사용하고 저장 payload에 포함할 수 있음
- **`strategy/create-strategy` 중간부터 시작**: 이미 종목을 보유 중인 사용자가 기존 평단가·수량을 입력해 그 지점부터 전략을 시작하는 기능. 세 전략(INFINITE·PRIVACY·VR) 공통이며 등록 전용(수정 불가). `InitialHoldingsSection`이 공통 입력(평단가·수량)을 렌더하고, `useStrategyForm`의 `vrFields.avgPrice`/`quantity`를 그대로 `initialHoldings`(정수)·`initialAvgPrice`(소수)로 전송한다 — 곱하지 않는다(서버가 등록 시점 전일종가×보유수량으로 V값을 직접 계산). 수량>0이면 평단가>0 필수, 평단가>0이면 수량>0 필수(양방향 — 서버는 quantity<=0이면 avgPrice를 payload에서 생략해 조용히 버리므로 UI가 선제 안내), 둘 다 음수·수량 소수 입력은 차단. 둘 다 미입력/0이면 두 필드 모두 생략(빈 포지션에서 시작)
- **`strategy/create-strategy` 증권사 제한**: 유형 메타 `supportedBrokers`(빈 배열·누락 = 전체 허용)에 계좌 증권사가 없으면 등록 유형 목록에서 숨기고 "<유형> 전략은 <증권사> 계좌에서만 등록할 수 있습니다" 안내를 남긴다(`useStrategyFormData`, 모의계좌는 문구에서 제외). 현재 PRIVACY = MERITZ·MOCK(주문은 장마감 30분 전 LIMIT VWAP) — 서버도 위반 시 400
- **`strategy/create-strategy` 시작예정일**: 등록 시 미래 날짜를 지정하면 그 이후 첫 거래일부터 매매가 시작되는 기능(exclusive 경계 — 지정일 자신도 skip될 수 있음). 세 전략 공통·등록 전용(수정·롤오버는 항상 오늘/기존 사이클 기준). `ScheduledStartSection`이 공용 `<Input type="date" min={todayKst()}>`를 렌더하고 안내 문구는 "선택한 날짜 이후 첫 거래일부터 시작됩니다"(절대 "그날부터"라고 쓰지 않는다). `useStrategyForm`의 `scheduledStartDate`가 설정돼 있으면 create payload에 그대로 전송하고, 비어 있으면 생략(서버가 오늘로 처리). 과거 날짜는 서버 400과 별개로 클라이언트에서도 `submitDisabledReason`으로 선제 차단(오늘 자신은 허용)
- **`strategy/create-strategy` VR 전략**: VR 등록은 기존 seed 입력을 초기 pool(`initialDeposit`)로 사용하고, `VrSettingsSection`에서 `intervalWeeks`, `bandWidth`, `recurringAmount`를 입력한다(평단가·수량은 위 공통 섹션에서 입력). 적립식(`recurringAmount > 0`)은 초기 pool 0을 허용하고, 거치/인출식은 초기 자산(추정 V값 + 초기 pool) 0을 차단한다. 인출식은 `(avgPrice × quantity) + initialDeposit >= abs(recurringAmount) * 100 * (4 / intervalWeeks)` 조건을 UI에서 먼저 검증한다(서버 V값은 시장가 기준이라 이 추정치와 다를 수 있음 — 최종 검증은 서버가 수행). 정수 전용 필드의 소수 입력은 보존한 뒤 검증에서 차단한다. VR은 백엔드가 `cycleSeedType=NONE`, `ticker=TQQQ`로 강제하므로 사이클 연속 UI를 숨긴다. 수정 모드는 평단가·수량을 저장값에서 역산할 수 없어 기존 V값을 읽기전용으로만 표시한다
- **`strategy/create-strategy` VR 램프 비활성화**: 고급 설정의 `gStepWeeks=0`은 gradient 램프 비활성화로 `gMax`·`gGraceWeeks`를 0으로 강제하고 입력을 잠근다. `pStepWeeks=0`도 같은 방식으로 poolLimitRate 램프를 비활성화해 `poolLimitFloor`·`pGraceWeeks`를 0으로 강제하고 잠근다. 단계주기를 다시 0이 아닌 값으로 바꾸면 종속 필드를 비워 재입력받는다
- **`strategy/create-strategy`·`reconfigure-vr` 서버 검증(api T10)**: 등록 `POST /api/accounts/{id}/trading-cycle-validations`·수정 `POST /api/trading-cycles/{id}/update-validations`·VR 재설정 `POST /api/trading-cycles/{id}/vr-config-validations`를 `useStrategyValidationQuery`(entities/strategy)로 400ms 디바운스해 부른다. 바디는 제출 바디 그대로(`buildStrategyPayload`·`toReconfigureVrRequest`), 쿼리 키가 바디라 늦게 온 이전 입력의 응답이 최신 결과가 되지 못한다. 제출 차단은 `current`(디바운스가 끝난 지금 입력의 응답)의 `fieldErrors`만 보고, 검증 대기·실패(404 사용자 복제본 없음·429/503·네트워크)는 막지 않는다 — 실제 제출을 서버가 다시 검증한다. 실패는 "입력값 사전 확인을 불러오지 못했습니다. 제출하면 서버가 다시 확인합니다."로 안내만 한다. 검증 POST는 저장이 없어 a11y-check·visual-diff 프록시의 읽기 전용 허용 목록(`READ_ONLY_POST`, `scripts/shared/browser.mjs`)에 있다. 429·503만 1회 재시도. Bean Validation 위반은 200이 아니라 400 ProblemDetail(`detail`만)로 와서 필드 없는 거절로 받는다(`derived`는 null). 같은 입력의 재조회(기본 staleTime 30초, 포커스 재조회 없음)가 실패해도 받아 둔 결과를 그 입력의 결과로 유지한다. 서버가 거절해 `derived`가 빈 경우는 최소 시드 확인 실패가 아니라 서버 사유를 보인다. 수정의 서버 거절은 보유·시작예정일 칸이 없어 하단에 둔다. 사유 우선순위는 로컬 guard(`strategyFormGuards`) → 서버 `fieldErrors`(요청 필드 `initialHoldings`·`initialAvgPrice`→보유 입력칸, `scheduledStartDate`→시작예정일, `recurringAmount`→적립금, 나머지 폼 하단). `warnings`(예: `AVAILABLE_CASH_EXCEEDED`)는 등록·수정 모두 서버 문장 그대로 `StrategyValidationWarnings`로 보이고 막지 않는다. 수정 검증은 시드 수정(보유 0, 바디 `initialDeposit`)일 때만 등록과 같은 `derived`(`basePrice`·`minSeed`·`skipReason`·`availableCash`, 시세 실패면 넷 다 null)를 준다 — 시드를 못 고치는 수정은 `derived`가 전부 null이다. 표시용 `derived`(최소 시드·기준가·가용 예수금)는 유형·종목·분할 수가 같은 동안 이전 응답을 유지한다(깜빡임 방지). 최소 시드로 시드를 채우는 것은 그 범위마다 지금 입력의 응답이 처음 올 때 한 번이다(시세 변동으로 사용자가 고친 시드를 덮지 않게).

## widgets

- **`strategy-detail`**: `useStrategyOrderPreviewQuery(strategyId)` 사용, 분할/리버스모드 배지 규칙 고정. VR은 `strategy.vr` 존재 여부로 운용 방식(적립식/거치식/인출식 + 금액), 밴드 폭, 주기, G, V, pool(현재 시작금액), pool 상한을 표시한다. `divisionCounts.length === 0`을 PRIVACY로 단정하지 않는다. `isScheduledStart(strategy)`가 true(시작예정일이 미래)면 상태 배지 그룹에 "N월 N일 시작예정" 배지(`--info`/`--info-bg` 토큰) 추가. 주문 내역의 방향·유형·상태 Select는 모바일에서 동일 너비 3열, PC에서 한 행으로 배치해 가로 넘침을 만들지 않는다. 필터는 기간 조회 결과에 AND 조건으로 적용한 뒤 페이지네이션하며, 필터 변경 시 1페이지로 초기화하고 원본 주문 없음과 필터 결과 없음을 서로 다른 빈 상태로 표시한다
- **`strategy-card`**: VR은 분할 배지 대신 compact `V $3,000.00` 형식의 배지를 표시한다. 왼쪽 변은 일시중지일 때만 회색(`--muted-foreground`)으로 표시하고(운영중은 미표시 — 주문 테두리와 색 의미가 겹치지 않게), 일시중지면 배지 행에 meta 라벨(`strategyStatuses`) 배지를 함께 둔다. 위/오른쪽/아래 변은 운영중일 때만 서버 `warnings` 코드로 표시하며 클라이언트는 판정하지 않고 코드→색·라벨만 매핑한다(`StrategyCard.tsx`의 `ORDER_SIGNAL_RULES`, 위에서부터 우선순위): `LEDGER_SHORTFALL`(빨강) > `ACCOUNT_CASH_PARTIAL`(주황) > `ACCOUNT_CASH_SHORTFALL`(빨강) > `HOLDINGS_SHORTFALL`(빨강) > `BUY_UNPLACED`·`SELL_UNPLACED`(주황). 해당 코드가 없고 오늘 접수된 주문이 있으면 녹색이다. 색만으로 전달하지 않도록 빨강·주황은 배지 텍스트를 배지 행에(라벨은 메타 `orderPreviewWarningCodes` — 배지가 한 줄 고정이라 금액은 넣지 않고 상세 배너에서 서버 detail 그대로 보여준다), 녹색은 `sr-only` 텍스트("오늘 주문 접수됨")를 함께 둔다. 리버스모드 배지는 모바일·PC 둘 다 표시한다. `isScheduledStart(strategy)`면 배지 행(모바일 1행·PC 배지 row)에 "N월 N일 시작예정" 배지 추가 — `AccountCard`의 compact 배지 행에는 넣지 않는다(혼잡 방지)
- **`strategy-card`·`strategy-detail` DCA 분기**: 래퍼에서 훅 호출 전에 `strategy.type === 'DCA'`만으로 분기한다(`&& dca` 아님). 전략 상세 페이지는 DCA면 SSR 미리보기 프리페치를 건너뛴다(목록 페이지의 계좌 배치 미리보기는 DCA도 포함한다 — 서버 `TradingPreviewService` 기준). DCA 상세는 원장 예수금(`ledgerDeposit`)과 원장 기준 `currentHoldings`·`avgPrice`(DCA 원장 값 — 계좌 전체 값 아님), 규칙 카드 목록, 규칙 열이 있는 페이지네이션된 `dca-executions` 이력을 보여준다

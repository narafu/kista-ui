# 가계부(finance) — 필요시 Read

entities/features/widgets에 흩어져 있던 가계부 서술을 원 출처별 절로 모은 문서다.

## entities

- **finance**: `/api/finance/*` 네임스페이스 하나를 소비한다. 리소스는 자산 스냅샷(`asset-snapshots`)·카테고리(`categories`, 4타입 CRUD)·계좌(`accounts`, CRUD)·월 마감(`monthly-closings`)·그룹(`groups`/멤버/초대)·거래내역(`transactions`)·예산(`budgets`). `AssetSnapshot.categoryId`는 `finance_categories`(그룹 소유 2계층 트리) FK — 응답의 `rootCategoryId`·`categoryName`·`accountName`을 그대로 렌더링에 쓰고 별도 이름 조회가 필요 없다. `assetClass`(`AssetClass` 6값: CASH/EQUITY/FIXED_INCOME/COMMODITY/CRYPTO/REAL_ESTATE)와 `market`(`Market` 2값: DOMESTIC/GLOBAL)은 서버가 정의한 닫힌 enum이라 `useMeta()`의 `assetClasses`/`markets`(`MetaBundle`, `labelOf('assetClasses'|'markets', code)`)로 라벨을 얻는다. 자산(ASSET) L1 카테고리 4개는 고정 UUID 시스템 시드(`f1000000-...-0401`~`0404`, 예적금/부동산/투자/대출 — `SYSTEM_INVESTMENT_CATEGORY_ID` 등 4개 상수로 export)라 구 `AssetCategory` enum과 동일한 4값 구조가 유지된다. 부채(순자산·구성비 분모) 판정은 반드시 `isLiability(snapshot)`(`rootCategoryId === SYSTEM_LOAN_CATEGORY_ID`)로 하고 문자열 비교를 반복하지 않는다. `categoryName`이 응답에 없는 집계 결과(`calcCategoryBreakdown` 등, `{category: L1 id, amount}` 형태)의 라벨은 `formatAssetL1CategoryLabel(id)`로 얻는다. `lib/aggregate.ts`가 위젯 공용 집계 함수를 전부 소유 — `calcCategoryComposition`(대출 포함)과 `calcAssetClassComposition`(대출 제외)은 범용 `calcComposition`을 위젯에서 직접 호출하지 말고 이 두 래퍼를 통해서만 쓴다. 자산 등록 폼의 카테고리 Select는 기존 카테고리(L1+L2) 선택만 가능하다 — 새 세부카테고리 생성은 `/finance` 설정 탭(`features/finance/manage-categories`)에서 한다. 단건 GET·벌크 삭제 엔드포인트가 여전히 없어 `loadAssetSnapshotById`는 전체 목록에서 find하고 `useDeleteManyAssetSnapshotsMutation`은 개별 DELETE를 `Promise.allSettled`로 병렬 호출한다. 월 마감은 `PATCH /monthly-closings/{month}`.
  - **그룹 스코프**: kista-api는 2026-08부터 1인 1그룹 정책이고, 모든 finance 리소스의 그룹 스코프를 호출자의 실제 소속(`findCurrentGroupId(userId)`)으로 판정한다 — 클라이언트는 그룹을 지정할 수 없다(목록 API가 `groupId` 파라미터를 받지 않음). 그래서 `financeKeys`의 list factory와 `entities/finance/api` 목록 함수, `*ListQueryOptions`에는 그룹 인자가 없고, SSR 프리페치도 `getAuthToken()`만으로 클라이언트 캐시 키와 일치한다. 소속이 바뀌는 mutation(초대 수락 `useRespondToInvitationMutation`, 초대 발급 `useCreateFinanceGroupInvitationMutation` — 무그룹이면 그룹 생성, 탈퇴·추방 `useRemoveFinanceGroupMemberMutation`)은 `financeKeys.all`을 무효화해 전 목록을 새 스코프로 재조회한다. 클라이언트가 그룹 id를 알아야 하는 곳은 월 마감 판정뿐이다 — 마감 목록에 개인 행과 그룹 행이 섞여 오므로 `useMonthlyClosingScopeGroupId()`(= `useFinanceGroupsQuery().data?.[0]?.id`)로 행을 고른다.
  - **카테고리 CRUD**: 생성 POST는 `type` 필수(누락 시 400이 아니라 오분류된 409). **PUT은 `parentId`/`type`을 서버가 무시**한다 — 이름·정렬순서만 실제 반영(카테고리 이동 불가). 삭제는 하위 트리 전체 cascade 소프트 삭제이며 참조 중인 과거 스냅샷은 그대로 유지된다(서버가 참조 검사 안 함). 시스템 카테고리(`system:true`)는 그룹 스코프 엔드포인트(`/api/finance/categories`)에서 수정·삭제 시 서버가 403. 카테고리 생성 다이얼로그(`CategoryFormDialog`/`SystemCategoryFormDialog`)는 `getCascadeLevels`로 임의 depth 계단식 부모 Select를 구성한다 — depth 제한 없음. 카테고리 뮤테이션(`useCreateFinanceCategoryMutation` 등)은 다른 finance 리소스와 달리 **`invalidateQueries` 후 재조회** 방식이다(POST/PUT 응답의 `children`이 항상 `[]`로 고정돼 있어 `upsertById` 직접 캐시 쓰기가 트리를 깨뜨리기 때문)
  - **거래내역(`transactions`)·예산(`budgets`)** — 수입/소비/저축 탭(`app/(main)/finance/(dashboard)/(flow)/{income,expense,saving}/page.tsx` + 공유 client 훅 `useFinanceFlowData.ts`)이 소비한다. `FinanceTransactionResponse`엔 `type`/`categoryName`/`rootCategoryId`가 없다 — 한 `GET /transactions`가 세 타입을 섞어 반환하므로 `lib/categoryIndex.ts`의 `buildCategoryIndex({INCOME,EXPENSE,SAVING})`(세 트리를 한 번에 순회)로 `categoryId -> {type, rootId, name}` 인덱스를 만들고 `lib/flowAggregate.ts`의 `filterByType`로 탭을 나눈다. 삭제된 카테고리를 가리키는 거래는 이 인덱스에 없다(카테고리 삭제가 소프트 삭제라 `GET /categories`가 반환 안 함) — 그런 거래는 어느 탭 집계에도 넣지 않고 `unclassifiedTransactions()`로 별도 노출한다("분류할 수 없는 내역"). 조회 기간은 월간 모드면 `lib/period.ts`의 `windowRange(month)`(12개월 슬라이딩 윈도우, 요약·전월대비·6개월추이를 커버)를, 연간 모드면 `periodRange(period, today)`를 그대로 `useFinanceFlowData.ts`의 `flowWindow`로 조회한다 — 요약·예산대비·내역 리스트가 이 하나를 공유한다(위젯마다 따로 쿼리하지 않는다). `periodRange`는 연간 모드에서 선택 연도가 올해면 1월~오늘(YTD), 이미 끝난 과거 연도면 1월~12월 전체를 반환한다(연간 모드엔 `Period.month`의 mm을 바꿀 UI가 없어 그 값을 범위 계산에 쓰면 안 된다 — 월간 탭에서 남은 값이 그대로 있을 수 있다). `elapsedMonthsInYear`·`calcBudgetProgress`(`toMonth`)·`calcFlowTrend`의 연간 버킷·`yearsRange`도 전부 같은 규칙을 따른다. 추이 차트만은 `flowWindow`가 아니라 `trendWindow(period, range, today)`(`TrendRange` = 버킷 수 또는 `'all'`, `'all'`이면 `from` 생략 — 서버가 하한 없이 조회)로 별도 조회하고, `calcFlowTrend(..., 'all')`은 가장 오래된 거래의 월/연도부터 버킷을 만든다. "전년대비"는 이 윈도우로 커버되지 않는 범위라 `previousYearRange(period, today)` 기준의 별도 쿼리를 `enabled: mode==='yearly'`로만 조건부 실행한다(`useFinanceFlowData.ts`→`FinanceSummary`) — `periodRange`와 대칭을 유지하려고 올해는 전년의 "오늘과 동일한 일자"까지, 과거 연도는 전년 1월~12월 전체로 계산한다(비대칭이면 전년 쪽에 최대 한 달치 거래가 더 들어가 델타가 왜곡된다). `FinanceBudgetResponse.amount`는 월 할당액이고 `calcBudgetProgress`가 YTD 모드에서 곱하는 배수는 "경과 개월 수"가 아니라 "YTD 범위 중 그 예산이 실제로 유효했던 개월 수"다(예산 시작일이 연중이면 그 이전 달은 배수에서 빠진다). 예산은 INCOME/EXPENSE/SAVING 카테고리에 걸 수 있다(ASSET 카테고리 예산 등록만 kista-api가 400) — 세 타입 모두 대상이라 `features/finance/manage-budgets/BudgetManager`는 세그먼트 없이 라우트(`/finance/budgets/[type]`)가 경로에서 고정해 넘긴 `type` prop 하나로 동작한다. 거래·예산 뮤테이션은 캐시 키에 조회 범위(from/to)가 섞여 있어 카테고리와 동일하게 `invalidateQueries(financeKeys.transactionsRoot()|budgetsRoot())` 방식이다(월 스코프 캐시에 saved 항목을 직접 upsert하려면 "어느 윈도우 캐시에 속하는지" 판정이 필요해 더 복잡하다)
  - **관리자 시스템 카테고리 CRUD**: `/api/admin/finance/categories`(GET/POST/PUT/DELETE)는 같은 `FinanceCategoryResponse`/`FinanceCategoryRequest` 형태를 재사용하지만 `groupId=null`·`system:true`로 고정된 공통 카테고리를 관리한다. `listSystemFinanceCategories`/`createSystemFinanceCategory`/`updateSystemFinanceCategory`/`deleteSystemFinanceCategory`(`entities/finance/api`)와 `useSystemFinanceCategoriesQuery`/`useCreateSystemFinanceCategoryMutation`/`useUpdateSystemFinanceCategoryMutation`/`useDeleteSystemFinanceCategoryMutation` 훅이 그룹 스코프 카테고리 함수·훅과 완전히 분리돼 있다. 캐시도 `financeKeys.systemCategoriesRoot()`/`systemCategories(type)`로 별도 네임스페이스라 그룹 스코프 `categoriesRoot()`를 침범하지 않는다. `useFinanceGroupsQuery()`를 구독하지 않는다(구독 시 admin 전용 화면에서 불필요하게 `/api/finance/groups`가 호출됨)
  - **계좌 CRUD**: flat 목록이라 기존 `upsertById`/`synchronizeListQueries` 하우스 패턴 그대로. 응답 `accountNo`는 서버가 복호화한 평문(마스킹 없음) — 목록 UI에서 뒷자리만 노출하는 건 UI 책임
  - **그룹**: 생성/삭제/이름수정 API가 없다 — 공유 그룹은 개인 그룹에서 초대 코드 발급(`useCreateFinanceGroupInvitationMutation`, OWNER 전용) → 수락(`useRespondToInvitationMutation`)으로만 생긴다. 초대 코드는 발급 응답에서 한 번만 내려오고 재조회 불가. 멤버 응답(`FinanceGroupMember`)엔 `userId`/`role`만 있고 닉네임이 없어 `nickname ?? userId.slice(0,8)` 폴백이 최종 형태다. `useRemoveFinanceGroupMemberMutation(groupId)`은 탈퇴/추방 겸용(variables=대상 userId, 본인 또는 OWNER만 가능) — 개인 그룹 탈퇴는 서버가 409
- **월 마감 쓰기 동결**: 마감(`MonthlyClosing.completed`)된 달은 kista-api가 재무 기록(자산 스냅샷·수입/소비/저축 거래)의 등록·수정·삭제·그룹 공유 전환을 409로 막는다. UI는 `isMonthClosed(closings, month, scopeGroupId)`(`entities/finance`)로 제출·행 작업을 선제 잠근다. 스코프는 반드시 `useMonthlyClosingScopeGroupId()`(실제 그룹 소속)로 넘기고 쿠키 `activeGroupId`는 쓰지 않으며(클라이언트 활성 그룹이 서버 판정과 어긋나 그룹 멤버 마감 미반영 버그를 냈다), 클라이언트 그룹 스코프를 다시 도입하거나 `closings.find(c => c.month === m)`를 단독으로 쓰지 않는다.

## features

- **`asset/save-asset`**: `AssetForm`이 `mode: 'create' | 'edit' | 'duplicate'` 하나로 3형태를 처리한다(네이티브 `useState` + `<form onSubmit>`, RHF+zod 아님 — strategy 도메인 전용 패턴). 카테고리(`categoryId`)·계좌(`accountId`)·자산군(`assetClass`)·시장(`market`)은 각각 독립 `Select`다(연쇄 리셋 없음). `assetClass`/`market` 기본값은 각각 `'CASH'`/`'DOMESTIC'`으로 고정해 사용자가 직접 고르게 한다. 로컬 `ComboField`(자유 입력 `Input` + 추천 `Select`)는 이제 `strategy`(운용전략 자유 메모) 한 곳에만 쓰이고, 추천 목록은 `@entities/user`의 `useMeQuery().data.strategySuggestions`(유저별 설정)에서 가져온다 — `@entities/finance`는 다른 entity를 import할 수 없어(entities 간 cross-import 금지) 두 entity를 조합하는 지점이 이 feature다. 카테고리 Select는 `@entities/finance`의 `getCascadeLevels`/`getCategoryPath` 기반 계단식 Select다 — depth 무관하게 동작하도록 설계돼 트리가 2단을 넘어 깊어져도 이 컴포넌트는 수정할 필요가 없다. `selectedPath: string[]` 상태 하나로 각 단의 선택값을 담고, edit/duplicate 모드는 `getCategoryPath`로 기존 `categoryId`에서 경로를 역산해 복원한다. 계좌는 선택(nullable), asset class/market 라벨은 `@entities/meta`의 `useMeta().meta.assetClasses`/`markets`에서 가져온다. 운용전략 필드는 L1이 '투자'(`isInvestmentCategoryId`)일 때만 화면에 노출된다 — 단 payload의 `strategy`는 항상 현재 상태값을 그대로 전송한다(카테고리 무관 자유 필드라는 구 설계 그대로, 비노출이 곧 서버 제출값 삭제를 의미하지 않는다). 값이 지워지는 시점은 사용자가 L1 Select를 '투자'가 아닌 값으로 능동적으로 바꿀 때뿐 — edit 모드 진입 시 레거시 기록(비-투자 카테고리에 저장된 기존 strategy 값)을 복원하는 경로는 건드리지 않아 데이터가 조용히 유실되지 않는다
- **`finance/save-transaction`**: 수입/소비/저축 탭의 거래내역 CRUD. `TransactionFormDialog`(create/edit 겸용, `AssetForm`과 동일하게 네이티브 `useState`+계단식 카테고리 Select)는 **라우트가 아니라 다이얼로그**다 — 거래내역 단건 GET이 없어 라우트 진입 시 id만으로 조회가 불가능하고, 목록 캐시에 이미 데이터가 있는 다이얼로그가 더 단순하기 때문. `NewTransactionButton`은 `NewAssetButton`(라우트 이동)과 달리 자체 `open` state로 다이얼로그를 열고 닫는 완전히 자기 완결적인 컴포넌트다 — **다이얼로그는 `open && <TransactionFormDialog .../>`처럼 조건부로만 마운트한다**(상시 마운트하면 내부 `useState`가 다음 열림에도 초기화되지 않고 이전 입력값이 남는다, `CategoryManager`의 `formTarget` 패턴과 동일 이유). `TransactionFormDialog`의 `windowFrom`/`windowTo` prop은 호출부에 따라 의미가 다르다 — 등록은 "오늘 기준" 독립 창(하한 없음, 상한은 이번 달 말일 — 과거 연도 등록도 허용), 수정은 "지금 조회 중인" 12개월 창(자세한 이유는 `TransactionFormDialog` 주석 참고). 삭제 확인은 `finance/delete-transaction`이 아니라 `shared/ui/ConfirmDeleteDialog`(제목·설명 문구만 받는 범용 삭제 확인 다이얼로그)를 직접 쓴다
- **`finance/manage-budgets`**: 예산 CRUD. Dialog가 아니라 인터셉팅 라우트다 — 목록 `/finance/budgets/[type]`(진입: `FinanceHeader` "예산 관리" 링크), 추가 `/new`(`?duplicateFrom=` 복제, `?categoryId=` 카테고리 프리필 — `FinanceBudgetProgress` "예산 미설정 → 예산 추가" 링크가 이걸로 폼 직행), 수정 `/[id]/edit`. 일반 페이지와 `@modal` 버전이 `app/(main)/finance/budgets/[type]/**/XxxBody.tsx`를 공유하고, Body가 카테고리·예산 목록을 서버에서 조회해 하이드레이션하며 수정·복제 원본을 prop으로 넘긴다(예산 단건 GET 없음 — 목록에서 찾음, 다른 type 예산 id면 404). `BudgetForm`은 `dismiss`(`push`→목록 이동 / `back`→`router.back()`)로 종료를 분기하고 제목은 Body의 `PageHeader`가 맡는다. `BudgetManager`는 `type: FlowType` prop을 받고 필터·페이지를 URL에 보존한다(`docs/agents/app.md` 인터셉팅 라우트 항목). 예산은 EXPENSE·SAVING뿐 아니라 INCOME 카테고리에도 걸 수 있다(ASSET만 kista-api가 400). 카테고리 기간 중첩(`finance_budgets_no_overlap`) 위반은 409로 오고 `useCreateFinanceBudgetMutation`/`useUpdateFinanceBudgetMutation`이 서버 메시지를 그대로 toast로 노출한다(별도 문구 분기 불필요)
- **`finance/manage-strategy-suggestions`**: 자산 등록 폼 추천 목록 — 유저별 설정(`user_settings.strategy_suggestions`, `PUT /api/settings/strategy-suggestions`)이라 ADMIN 게이트 없이 모든 로그인 유저에게 노출된다. `/finance` 설정 탭(계좌관리 아래) 위치는 유지 — 자산 등록 폼 전용 값이라 일반 계정 설정(`/settings`)보다 finance 도메인에 두는 게 자연스럽다는 판단. 값은 `@entities/user`의 `useMeQuery().data.strategySuggestions`, 저장은 `useUpdateStrategySuggestionsMutation`이 `{suggestions}`만 PUT한다(엔드포인트가 이 필드 하나만 받는 부분 갱신). `SuggestionListEditor`(`shared/ui`) 조작마다 즉시 반영하는 UX는 유지
- **`finance/manage-categories`**: `/finance` 설정 탭의 카테고리 CRUD. `CategoryManager`가 4타입(ASSET/INCOME/EXPENSE/SAVING) 세그먼트(`shared/ui/SegmentedToggle`, 가계부 탭바 `SectionTabBar`와 같은 시각 패턴)를 소유하고 `useFinanceCategoriesQuery(type)` 트리를 L1+`children` 들여쓰기로 렌더한다. 생성/수정은 `CategoryFormDialog`(Base UI `Dialog`) 하나가 겸용 — 수정 모드는 PUT이 `parentId`/`type`을 무시하는 서버 제약 때문에 이름·정렬순서만 노출한다. 트리 행(`CategoryRow`, 재귀)은 별도 파일로 추출돼 있고 `lockSystemCategories?: boolean`(기본 `true`)를 받는다 — 시스템 카테고리(`system:true`)는 기본적으로 수정·삭제 버튼을 비활성화한다(`shared/ui/ShareableRowActions`의 `locked` — `IconButton` native `disabled` + 흐림). 삭제 확인(`DeleteCategoryDialog`)은 `collectSubtreeIds`로 하위 개수를 세어 "하위 N개 카테고리가 함께 삭제됩니다" 문구를 만든다
  - **관리자용 시스템 카테고리**: `/admin/settings` 페이지에 배치된 `SystemCategoryManager`/`SystemCategoryFormDialog`(같은 슬라이스, `SystemCategoryManager`만 export)는 `/api/admin/finance/categories`(`app/api/admin/[[...path]]` catch-all 프록시, ADMIN role은 kista-api가 검증)를 소비해 `groupId=null`·`system:true`로 고정되는 공통 카테고리를 관리한다. 그룹 스코프 카테고리와 시나리오·권한·데이터소스가 달라 훅을 조건 분기하지 않고 완전히 별도 컴포넌트로 분리했다(`useSystemFinanceCategoriesQuery`/`useCreateSystemFinanceCategoryMutation` 등, 캐시 루트도 `financeKeys.systemCategoriesRoot()`로 분리). `CategoryRow`에 `lockSystemCategories={false}`를 넘겨 시스템 카테고리도 수정·삭제 가능하게 한다(이 화면 자체가 시스템 카테고리 관리 화면이므로 기본 잠금을 반전)
- **`finance/manage-accounts`**: `/finance` 설정 탭의 재무 계좌(은행/증권사/보험/거래소) CRUD — `entities/account`(한국투자증권 브로커 계좌)와는 다른 도메인이라 디렉토리·import를 절대 섞지 않는다. `AccountManager`가 목록에서 `accountNo`를 `maskAccountNo`(뒷 4자리만 노출)로 마스킹해 렌더하고, 수정 다이얼로그에서만 전체 값을 편집한다. 목록 상단 계좌타입 필터·정렬(이름/유형/등록순) Select는 계좌 수가 적어 서버 API 없이 클라이언트 `useMemo`로 처리한다. 계좌도 공유/귀속 대상이다(`useShareFinanceAccountMutation`/`useUnshareFinanceAccountMutation`) — 단 flat 목록이라도 unshare는 소유자 아닌 그룹 멤버도 실행 가능해(caller의 group-scope 목록에서 항목이 사라져야 함) create/update와 달리 `upsertById`가 아니라 다른 finance 리소스와 동일하게 `accountsRoot()` invalidate 방식을 쓴다. 계좌번호는 서버가 신규/수정 요청에 숫자만 허용(`@Pattern`, 기존 DB 데이터는 마이그레이션하지 않음) — `AccountFormDialog`가 입력 시 `digitsOnly`로 즉시 strip하고, 수정 모드 초기값도 `digitsOnly`로 정규화해 비숫자 legacy 값을 건드리지 않고 다른 필드만 고쳐도 400을 맞지 않게 한다
- **`finance/manage-group`**: `/finance` 설정 탭의 그룹 멤버·초대. kista-api는 **1인 1그룹 정책**(개인 그룹 자동생성 없음)이라 `useFinanceGroupsQuery()`는 0개(무그룹=개인) 또는 1개(그룹 소속)만 반환하고 `FinanceGroup`에 `personal`·`name` 필드가 없다 — "그룹 소속 여부"(`groups.length`) 자체로 개인/그룹을 판정한다. `GroupManager`가 `groups`를 한 번만 구독하고, 그룹이 있으면 `GroupSection`(멤버 목록+탈퇴)을 렌더하며 없으면 초대 발급 안내만 보여준다 — 자식이 같은 쿼리를 다시 구독하지 않는다. **무그룹 유저가 초대를 발급하는 시점에 kista-api가 그 자리에서 새 그룹을 만들고 본인을 OWNER로 등록한다**(`POST /groups/{id}/invitations`의 path `id`는 이 경우 서버가 무시 — `GroupManager`가 무그룹일 때 `InviteDialog`에 `me.id`를 자리채움 값으로 넘긴다). 발급·수락·탈퇴·추방 mutation의 `financeKeys.all` 무효화는 위 그룹 스코프 항목 참고. 그룹 탈퇴·추방 시 데이터의 `group_id`는 **이관되지 않는다**(kista-api `leaveGroup`) — 탈퇴자는 더 이상 조회할 수 없고 남은 멤버는 계속 조회하므로, 안내 문구는 "더 이상 접근 불가"다. OWNER가 나가면 서버가 남은 멤버 중 가장 먼저 가입한 사람을 자동 승계한다. 1인 1그룹 정책상 이미 그룹에 소속된 유저는 다른 그룹 초대를 수락할 수 없어(서버가 거부) `AcceptInvitationForm`은 무그룹일 때만 노출한다. `isOwner` 게이팅은 `GroupSection`이 멤버 목록에서 내 role을 찾아 판정하고, 발급된 코드는 재조회가 안 되므로 다이얼로그가 열려 있는 동안만 표시하고 복사 버튼+경고 문구를 둔다. `AcceptInvitationForm`은 코드 입력 후 수락만 처리한다(코드를 본인이 직접 입력하는 흐름이라 거절 버튼 없음).
- **`finance/save-transaction`·`finance/manage-budgets` 그룹 공유 전환**: 개인 소유(`groupId` 없음) 거래내역·예산을 소유자의 현재 그룹으로 전환하는 `PATCH .../{id}/share`가 있다(`useShareFinanceTransactionMutation`/`useShareFinanceBudgetMutation`, 성공 시 각각 `transactionsRoot()`/`budgetsRoot()` 무효화). 역방향 `PATCH .../{id}/unshare`(`useUnshareFinanceTransactionMutation`/`useUnshareFinanceBudgetMutation`)도 있다 — 소유자 한정이 아니라 같은 그룹 멤버면 누구든 개인 소유로 되돌릴 수 있고, 되돌린 뒤 `userId`는 실행자가 아니라 기존 소유자 그대로 유지되며 이미 개인 소유면 멱등 200이다. 자산 스냅샷도 동일 패턴이다(`useShareAssetSnapshotMutation`/`useUnshareAssetSnapshotMutation`, `AssetSnapshotResponse.groupId`). `widgets/finance-record-list`·`widgets/asset-record-list`의 복제 버튼 옆, `manage-budgets/BudgetManager`의 수정 버튼 옆에 그룹 소속(`useFinanceGroupsQuery().length > 0`, `useCanShareToGroup()`) 상태에서 소유 형태에 따라 "공유"(`!item.groupId`) 또는 "귀속"(`item.groupId` 있음, 그룹 소유를 개인으로 되돌리는 버튼) 버튼 하나만 노출한다 — 무그룹 상태에서는 둘 다 없다. account는 `manage-accounts` 항목 참고. category는 트리 구조라 `PATCH .../{id}/share`·`.../unshare`가 대상 노드 하위 전체(임의 depth)를 cascade로 함께 전환한다(kista-api recursive CTE 벌크 UPDATE). `useShareFinanceCategoryMutation`/`useUnshareFinanceCategoryMutation`(`entities/finance`)이 `categoriesRoot()` 무효화 방식(다른 category 뮤테이션과 동일 패턴)을 쓴다. `manage-categories/CategoryRow`가 `canShare`/`onShare`/`onUnshare` prop을 재귀로 하위까지 전달해 각 행이 자신의(서버가 이미 cascade 반영한) `groupId`를 그대로 렌더한다 — system 카테고리(`category.system`)는 그룹 개념이 없어 버튼 자체가 렌더되지 않는다. `SystemCategoryManager`는 이 prop들을 넘기지 않아 관리자 화면엔 노출되지 않는다. **신규 생성도 `POST /{resource}?shareToGroup=true` 한 번으로 그룹 소유로 원자적으로 만든다** (5개 리소스 공통). 대상 그룹은 서버가 `userId`로 해석하므로 클라가 groupId를 보내지 않는다. `BudgetForm`/`TransactionFormDialog`/`CategoryFormDialog`의 생성 모드와 `AssetForm`의 생성/복제 모드(`mode!=='edit'`), `AccountFormDialog` 생성 모드에 "그룹으로 저장" 스위치가 있다 — `useCanShareToGroup()`으로 게이팅, 기본값 켜짐, 체크 시 `useCreateXxxMutation` variables에 `shareToGroup: true`를 얹으면 `createXxx(data, { shareToGroup })` 단일 호출로 끝난다(부분 실패 상태 없음). 예산 그룹 기간 겹침(EXCLUDE 409)은 create 자체가 실패로 반환한다(`onError` → `apiMsg` 토스트); 개인 스코프 겹침은 서버가 규칙대로 자동 트림/삭제한다. **카테고리는 계층이라 부모가 개인 소유면 서버가 400** — `CategoryFormDialog`가 선택된 부모의 `groupId` 유무(`getCategoryPath(l1Categories, parentId).at(-1)`)로 토글을 게이팅해, 개인 부모 아래에서는 토글을 숨기고 "개인 카테고리 하위에는 그룹 공유 카테고리를 만들 수 없습니다" 안내를 띄운다. `widgets/finance-bulk-register`(일괄 등록)도 같은 `?shareToGroup=true`로 서버가 각 항목을 그룹 소유로 생성하며(항목별 실패는 응답 `failures[]`), 기본값도 단건 폼과 동일하게 그룹 소속이면 켜짐(`useState(true)`)이다.

## widgets

- **`/finance`(가계부) 탭 구조**: 5탭(자산/수입/소비/저축/설정)이 각각 실제 라우트다 — `/finance`(자산, 첫 탭)·`/finance/income`·`/finance/expense`·`/finance/saving`·`/finance/settings`, 전부 `app/(main)/finance/(dashboard)/` 라우트 그룹(URL엔 드러나지 않음) 아래에 있다. `(dashboard)/layout.tsx`(Server)가 `assetSnapshots`/`monthlyClosing`/`financeGroupList` 공통 prefetch+`HydrationBoundary`와 `FinanceHeader`(client, 탭바+`PageHeader`, 활성 탭에 따라 actions 분기)를 소유하고, `/finance/new`·`/finance/bulk-register`·`/finance/[id]/edit`는 이 그룹 밖 형제 라우트라 탭 UI 영향을 받지 않는다(통계 메뉴와 동일 패턴, `docs/agents/architecture.md` 참고). `(dashboard)/page.tsx`가 자산 탭(5개 자산 위젯, `NewAssetButton`)을 담당하고, `settings/page.tsx`는 `widgets/asset-settings/AssetSettingsPanel`만 렌더한다. 수입/소비/저축 3탭(`(dashboard)/(flow)/income|expense|saving/page.tsx`)은 `widgets/finance-summary`·`widgets/finance-budget-progress`(2026-08부터 INCOME/EXPENSE/SAVING 전부 허용, 셋 다 예산 대비 렌더)·`widgets/finance-trend`·`widgets/finance-record-list`를 이 순서로, `type: FinanceCategoryType` prop 하나로 재사용한다(탭별 전용 위젯을 만들지 않는다) — 세부 데이터 흐름(12개월 윈도우 쿼리·카테고리 인덱스)은 이 문서 `## entities`의 거래내역·예산 항목 참고. 기간 상태(`Period = {month, mode}`)는 `(flow)/useFinanceFlowData.ts` 공유 client 훅이 URL 쿼리(`?month=&mode=`)에 실어 관리한다 — 서브라우트 전환으로 세 탭이 더 이상 한 컴포넌트가 아니라 React state 공유가 불가능해졌고, React Query 캐시는 전역이라 쿼리 결과 자체는 동일 키로 자동 공유되므로 탭 간 진짜로 이어줘야 하는 값은 이 period뿐이다. `PageHeader` actions는 `FinanceHeader`가 활성 라우트로 분기한다 — 자산 탭은 `NewAssetButton`, 수입/소비/저축 탭은 "예산 관리" 링크(`/finance/budgets/{slug}` 인터셉팅 라우트, 해당 탭 type 고정 — 모달이 떠 있는 동안에도 배경 헤더는 원래 탭 기준으로 판정)와 `NewTransactionButton`(`features/finance/save-transaction`, "거래내역 등록")이 나란히 노출된다
- **`asset-overview`/`asset-trend`/`asset-composition`/`asset-record-check`/`asset-record-list`**: 자산 탭을 구성하는 5개 슬라이스. 위젯끼리 cross-import가 금지돼 있고 Server Component는 함수를 prop으로 넘길 수 없어, `asset-overview`(월 선택 UI)와 `asset-record-check`(선택된 월 기준 점검)가 공유하는 "기준 월" 상태는 `app/(main)/finance/(dashboard)/page.tsx`(자산 탭 페이지 자체, app 레이어)가 소유하고 각 위젯에 `month`/`onMonthChange` prop으로 흘려보낸다 — `market-holiday-calendar`류의 `marketPanels` slot 패턴과 같은 이유의 같은 해법이다. `asset-trend`·`asset-composition`도 같은 `month` 상태를 받아(`AssetTrend`/`AssetComposition` Shell → Inner) 집계 창의 끝을 선택된 월로 앵커링한다(`calcMonthlyTrend`/`calcComposition`의 `endMonth` 인자) — 값이 없으면 최신 기록 기준(과거 동작)으로 폴백한다. 집계 창 길이는 카드 헤더(`CardAction`)의 `shared/ui/SegmentedToggle` 기간 선택(12/24/36개월/전체, `MONTHLY_TREND_RANGE_OPTIONS`)으로 고르며, `'all'`은 `monthsLimit=Infinity`로 넘겨 기록 전체 월을 쓴다. 기간 상태(`trendMonths`, 연간 차트는 `trendYears` 5/10년/전체)는 `FinancePeriodProvider`가 소유해 자산 두 차트와 수입/소비/저축 월간 추이가 공유하고 탭 전환 후에도 유지된다(새로고침엔 초기화). 수입/소비/저축 추이는 요약·내역용 `flowWindow`와 별개로 `trendWindow(period, range)` 쿼리를 쓴다(`'all'`은 `from` 없이 조회, 월간 12개월은 `windowRange`와 같은 키라 캐시 공유) — 로딩도 분리돼 기간 변경 시 추이 카드만 스켈레톤이 된다. `asset-trend`(recharts LineChart)·`asset-composition`(recharts 스택 BarChart ×2)은 각각 Shell + `next/dynamic({ ssr: false })` Inner 분리 구조이며, `react-doctor/prefer-dynamic-import` 룰은 파일 간 도달 가능성을 보지 않고 recharts 정적 import를 항상 감지하므로 기존 recharts 위젯과 동일하게 `// eslint-disable-next-line react-doctor/prefer-dynamic-import`를 import 직전 줄에 둔다(설명 주석은 disable 지시문보다 앞에 — 지시문과 import 사이에 다른 줄이 끼면 타겟팅이 깨진다). 모바일/PC 모두 추이-구성비 순서다. 순자산·카테고리별/자산군별 현황·구성비 계산은 전부 `entities/finance/lib/aggregate.ts`의 순수 함수를 공유한다(위젯 계층에 중복 구현 금지). `assetClass`/`market`은 서버 닫힌 enum이라 라벨은 `useMeta()`의 `labelOf('assetClasses'|'markets', code)`로 얻고, L1 카테고리 라벨은 `formatAssetL1CategoryLabel(id)`로 얻는다(위젯에서 직접 라벨 맵을 두지 않는다)
- **가계부 금액 감추기**: 설정 탭 토글(`features/finance/hide-amounts`, localStorage 영구)과 `FinanceHeader` 눈 아이콘(세션 한정 일시 공개, 가계부를 떠나면 해제)이 `shared/lib/hooks/use-amount-hidden.ts` 모듈 스토어(`useSyncExternalStore`)를 공유한다. 자산·수입·소비·저축 탭에서 금액을 표시하는 위젯은 `fmtKrw`/`fmtSignedKrw` 결과를 반드시 `maskIfHidden()`으로 감싼다(새 위젯·새 표시 지점 추가 시 누락 주의). KPI 요약은 `masked`일 때 `RevealableValue`로 값별 보기 버튼을 둔다. 차트 Y축 눈금(만원 축약)과 탭 밖 화면(예산 관리·일괄 등록)은 의도적으로 마스킹하지 않는다. SSR·hydration 첫 렌더는 설정을 읽기 전(`hidden === null`)이라 가린 상태로 그린다 — 실제 금액이 깜빡이지 않게 하기 위함
- **`asset-settings/AssetSettingsPanel`**: `/finance` 설정 탭의 조합 위젯. `features/finance/manage-categories`(카테고리 CRUD)·`manage-accounts`(계좌 CRUD)·`manage-strategy-suggestions`(운용전략 추천 목록 — 계좌관리 아래)·`manage-group`(그룹 멤버·초대)을 `SettingsPageContent`와 동일한 "Surface 카드로 묶기" 패턴으로 나열한다. 화이트리스트 밖 페이지 위젯이라 다른 widget에서 import 금지 — `app/(main)/finance/(dashboard)/settings/page.tsx`(app 레이어)만 마운트한다

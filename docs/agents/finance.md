entities/features/widgets에 흩어져 있던 가계부 서술을 원 출처별 절로 모은 문서다.

## entities

- **finance**: `/api/finance/*` 네임스페이스 하나를 소비한다. 리소스는 자산 스냅샷(`asset-snapshots`)·카테고리(`categories`, 4타입 CRUD)·계좌(`accounts`, CRUD)·월 마감(`monthly-closings`)·그룹(`groups`/멤버/초대)·거래내역(`transactions`)·예산(`budgets`). `AssetSnapshot.categoryId`는 `finance_categories`(그룹 소유 2계층 트리) FK — 응답의 `rootCategoryId`·`categoryName`·`accountName`을 그대로 렌더링에 쓰고 별도 이름 조회가 필요 없다. `assetClass`(`AssetClass` 6값: CASH/EQUITY/FIXED_INCOME/COMMODITY/CRYPTO/REAL_ESTATE)와 `market`(`Market` 2값: DOMESTIC/GLOBAL)은 서버가 정의한 닫힌 enum이라 `useMeta()`의 `assetClasses`/`markets`(`MetaBundle`, `labelOf('assetClasses'|'markets', code)`)로 라벨을 얻는다. 자산(ASSET) L1 카테고리 4개는 고정 UUID 시스템 시드(`f1000000-...-0401`~`0404`, 예적금/부동산/투자/대출 — `SYSTEM_INVESTMENT_CATEGORY_ID` 등 4개 상수로 export)라 구 `AssetCategory` enum과 동일한 4값 구조가 유지된다. 자산 집계(요약·전월 요약·추이·구성비·기록 점검)는 kista-api 서버 집계 엔드포인트(`/asset-snapshots/{summary,trend,composition,check}`)가 하고 UI는 응답을 그린다(위젯에서 스냅샷 목록으로 다시 계산하지 않는다). 부채(대출) 제외·구성비 분모 같은 규칙도 서버 소유다. 집계 결과는 L1을 `categoryId`로만 주므로 라벨은 `formatAssetL1CategoryLabel(id)`로 얻고, 기록 점검의 누락 계좌 라벨("계좌 미지정"·자산군 라벨)은 UI가 메타로 조립한다. 자산 탭 기본 월은 월 없이 조회한 `summary`의 `month`(최근 기록 월)이다(자산 탭 `(dashboard)/page.tsx`가 프리페치하고 이어서 그 달 `assetSnapshotListQueryOptions(month)`도 프리페치한다. 사용자가 월을 고르기 전엔 `AssetOverview`도 같은 월 없는 키를 써 첫 진입에 한 번만 받는다). 자산 기록 목록(`GET /asset-snapshots`)은 `month` 필수의 월 전량형이다 — 서버가 그 달만 주고(월 없으면 400) 카테고리 하위트리·자산군·시장·메모 필터와 정렬은 전량 안의 즉시 반응이라 UI(`AssetRecordList`)가 한다. 목록 응답은 `{ items }` 봉투이고 API 함수(`entities/finance/api`)가 풀어 배열로 돌려준다. 자산 등록 폼의 카테고리 Select는 기존 카테고리(L1+L2) 선택만 가능하다 — 새 세부카테고리 생성은 `/finance` 설정 탭(`features/finance/manage-categories`)에서 한다. 단건 GET·벌크 삭제 엔드포인트가 여전히 없어 `loadAssetSnapshotById(id, month, token)`는 그 달 목록에서 find하고(목록의 편집·복제 링크가 `?month=`를 싣는다, month 없으면 null) 자산 수정·삭제 뮤테이션은 월별 목록 캐시를 upsert하지 않고 `assetSnapshotsRoot()`·`aggregatesRoot()`를 invalidate하며(수정으로 기준일이 다른 달로 옮겨질 수 있다), `useDeleteManyAssetSnapshotsMutation`은 개별 DELETE를 `Promise.allSettled`로 병렬 호출한다. 월 마감은 `PATCH /monthly-closings/{month}`.
  - **그룹 스코프**: kista-api는 2026-08부터 1인 1그룹 정책이고, 모든 finance 리소스의 그룹 스코프를 호출자의 실제 소속(`findCurrentGroupId(userId)`)으로 판정한다 — 클라이언트는 그룹을 지정할 수 없다(목록 API가 `groupId` 파라미터를 받지 않음). 그래서 `financeKeys`의 list factory와 `entities/finance/api` 목록 함수, `*ListQueryOptions`에는 그룹 인자가 없고, SSR 프리페치도 `getAuthToken()`만으로 클라이언트 캐시 키와 일치한다. 소속이 바뀌는 mutation(초대 수락 `useRespondToInvitationMutation`, 초대 발급 `useCreateFinanceGroupInvitationMutation` — 무그룹이면 그룹 생성, 탈퇴·추방 `useRemoveFinanceGroupMemberMutation`)은 `financeKeys.all`을 무효화해 전 목록을 새 스코프로 재조회한다. 클라이언트가 그룹 id를 알아야 하는 곳은 월 마감 판정뿐이다 — 마감 목록에 개인 행과 그룹 행이 섞여 오므로 `useMonthlyClosingScopeGroupId()`(= `useFinanceGroupsQuery().data?.[0]?.id`)로 행을 고른다.
  - **카테고리 CRUD**: 생성 POST는 `type` 필수(누락 시 400이 아니라 오분류된 409). **PUT은 `parentId`/`type`을 서버가 무시**한다 — 이름·정렬순서만 실제 반영(카테고리 이동 불가). 삭제는 하위 트리 전체 cascade 소프트 삭제이며 참조 중인 과거 스냅샷은 그대로 유지된다(서버가 참조 검사 안 함). 시스템 카테고리(`system:true`)는 그룹 스코프 엔드포인트(`/api/finance/categories`)에서 수정·삭제 시 서버가 403. 카테고리 생성 다이얼로그(`CategoryFormDialog`, 시스템 카테고리는 `system` prop)는 `getCascadeLevels`로 임의 depth 계단식 부모 Select를 구성한다 — depth 제한 없음. 카테고리 뮤테이션(`useCreateFinanceCategoryMutation` 등)은 다른 finance 리소스와 달리 **`invalidateQueries` 후 재조회** 방식이다(POST/PUT 응답의 `children`이 항상 `[]`로 고정돼 있어 `upsertById` 직접 캐시 쓰기가 트리를 깨뜨리기 때문)
  - **거래내역(`transactions`)·예산(`budgets`)** — 수입/소비/저축 탭(`app/(main)/finance/(dashboard)/(flow)/{income,expense,saving}/page.tsx` + 공유 client 훅 `useFinanceFlowData.ts`)이 소비한다. `FinanceTransactionResponse`엔 `type`/`categoryName`/`rootCategoryId`가 없다 — 행 렌더(이름·색)는 `lib/categoryIndex.ts`의 `buildCategoryIndex({INCOME,EXPENSE,SAVING})`로 만든 `categoryId -> {type, rootId, name}` 인덱스를 쓴다. 탭 분리(`type`)는 서버가 한다 — 삭제된(목록 밖) 카테고리의 거래는 서버가 `type` 필터에서 제외해 어느 탭에도 안 보이고, "분류할 수 없는 내역" 안내는 없다. 요약(합계·전월·전년 동기간·월평균·남은 금액·수입 대비 비율)·추이·예산 대비는 서버 집계 엔드포인트(`/transactions/{summary,trend,budget-progress}`, `type`·`mode=MONTHLY|YEARLY`·`month`, 기준일은 서버 Clock KST)를 각 위젯이 직접 조회한다 — YTD 범위·전년 동기간 대칭·예산 유효 개월 배수 같은 기간 규칙은 서버(kista-api FlowPeriod) 소유다. 거래 목록은 커서 페이지형이다 — `useFinanceTransactionsInfiniteQuery`가 서버 `type`·`categoryId`(하위 트리 포함)·`memo`(디바운스)·`sort`(`key,dir`)·`from/to`(`periodRange(period, today)`: 월간은 그 달, 올해는 1월~오늘, 과거 연도는 1~12월 — 연간 모드의 `Period.month` mm은 신뢰하지 않는다)로 조회하고 "더 보기"(`LoadMoreButton`)로 이어 받는다. 커서는 같은 sort에서만 유효해(다르면 400) 조건이 바뀐 새 키 첫 응답 전(`isPlaceholderData`)엔 더 보기를 막는다. 자동 월 보정은 오늘 기준 12개월 범위의 최신 거래 1건(`useLatestTransactionDateQuery`, 세 타입 전체)을 조회해 `autoAdjustedMonth`가 "거래가 있는 최근 달"로 옮긴다. 자동 월 보정이 끝나기 전(`isPeriodPending`)엔 집계 위젯이 로딩으로 그리고 조회를 미룬다. 추이 기간 `TrendRange`의 `'all'`은 `range`를 생략해 서버가 가장 오래된 거래부터 버킷을 만든다. 예산은 INCOME/EXPENSE/SAVING 카테고리에 걸 수 있다(ASSET 카테고리 예산 등록만 kista-api가 400) — 세 타입 모두 대상이라 `features/finance/manage-budgets/BudgetManager`는 세그먼트 없이 라우트(`/finance/budgets/[type]`)가 경로에서 고정해 넘긴 `type` prop 하나로 동작한다. 거래·예산 뮤테이션은 캐시 키에 조회 조건(from/to·type·categoryId·memo·sort)이 섞여 있어 카테고리와 동일하게 `invalidateQueries(financeKeys.transactionsRoot()|budgetsRoot())` 방식이다(커서 페이지 캐시에 saved 항목을 직접 upsert하려면 "어느 조건·페이지에 속하는지" 판정이 필요해 더 복잡하다)
  - **서버 집계 캐시**: 집계 쿼리 키는 전부 `financeKeys.aggregatesRoot()`(`['finance','aggregates',…]`) 하나 아래에 있다 — 집계 하나가 여러 원본에 걸려(예산 대비 = 거래·예산·카테고리, 일괄 등록 미리보기 = 자산·거래·카테고리, 자산 점검 = 자산·카테고리명) 원본 루트 prefix로는 의존을 표현할 수 없기 때문이다. 자산 기록(생성·수정·삭제·공유 전환)·거래·예산·카테고리 뮤테이션은 자기 루트와 함께 이 루트를 무효화한다(그룹 소속 변경·일괄 등록은 `financeKeys.all`이라 포함). 계좌는 수정·삭제·공유 전환만 함께 무효화한다(계좌명이 기록 점검·일괄 등록 미리보기에 실림, 생성은 집계에 영향 없음). 월 마감·시스템 카테고리 뮤테이션은 무효화하지 않는다. 집계 queryOptions는 `placeholderData: keepPreviousData`(`@shared/lib/query`)로 월·모드 전환 중 이전 응답을 유지하고, 연간 모드 키·요청의 month는 `YYYY-01`로 정규화한다
  - **관리자 시스템 카테고리 CRUD**: `/api/admin/finance/categories`(GET/POST/PUT/DELETE)는 같은 `FinanceCategoryResponse`/`FinanceCategoryRequest` 형태를 재사용하지만 `groupId=null`·`system:true`로 고정된 공통 카테고리를 관리한다. `listSystemFinanceCategories`/`createSystemFinanceCategory`/`updateSystemFinanceCategory`/`deleteSystemFinanceCategory`(`entities/finance/api`)와 `useSystemFinanceCategoriesQuery`/`useCreateSystemFinanceCategoryMutation`/`useUpdateSystemFinanceCategoryMutation`/`useDeleteSystemFinanceCategoryMutation` 훅이 그룹 스코프 카테고리 함수·훅과 완전히 분리돼 있다. 캐시도 `financeKeys.systemCategoriesRoot()`/`systemCategories(type)`로 별도 네임스페이스라 그룹 스코프 `categoriesRoot()`를 침범하지 않는다. `useFinanceGroupsQuery()`를 구독하지 않는다(구독 시 admin 전용 화면에서 불필요하게 `/api/finance/groups`가 호출됨)
  - **계좌 CRUD**: flat 목록이라 기존 `upsertById`/`synchronizeListQueries` 하우스 패턴 그대로. 응답 `accountNo`는 서버가 복호화한 평문(마스킹 없음) — 목록 UI에서 뒷자리만 노출하는 건 UI 책임
  - **그룹**: 생성/삭제/이름수정 API가 없다 — 공유 그룹은 개인 그룹에서 초대 코드 발급(`useCreateFinanceGroupInvitationMutation`, OWNER 전용) → 수락(`useRespondToInvitationMutation`)으로만 생긴다. 초대 코드는 발급 응답에서 한 번만 내려오고 재조회 불가. 멤버 응답(`FinanceGroupMember`)엔 `userId`/`role`만 있고 닉네임이 없어 `nickname ?? userId.slice(0,8)` 폴백이 최종 형태다. `useRemoveFinanceGroupMemberMutation(groupId)`은 탈퇴/추방 겸용(variables=대상 userId, 본인 또는 OWNER만 가능) — 개인 그룹 탈퇴는 서버가 409
- **월 마감 쓰기 동결**: 마감(`MonthlyClosing.completed`)된 달은 kista-api가 재무 기록(자산 스냅샷·수입/소비/저축 거래)의 등록·수정·삭제·그룹 공유 전환을 409로 막는다. UI는 `isMonthClosed(closings, month, scopeGroupId)`(`entities/finance`)로 제출·행 작업을 선제 잠근다. 스코프는 반드시 `useMonthlyClosingScopeGroupId()`(실제 그룹 소속)로 넘기고 쿠키 `activeGroupId`는 쓰지 않으며(클라이언트 활성 그룹이 서버 판정과 어긋나 그룹 멤버 마감 미반영 버그를 냈다), 클라이언트 그룹 스코프를 다시 도입하거나 `closings.find(c => c.month === m)`를 단독으로 쓰지 않는다.
